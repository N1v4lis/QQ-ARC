## 一句话结论

控制台从"横向页签 + 旧皮肤"重构为**左侧导航 + 自绘标题栏 + 时间轴详情**，
配色与排版以 DeepSeek Harness（DSH）的**真实设计令牌**为基底；
默认跟随系统亮/暗，支持三档手动切换；全部动效统一由一套令牌驱动。
移植来的业务逻辑（12 段前端脚本 + 全部后端接口）**一行未改地保持可用**。

## 设计基底的来源（不是"照着感觉做"）

DSH 的客户端主题包里有完整的三层令牌体系，我把它**整包搬了过来**：

| 层 | 例子 | 来源 |
|---|---|---|
| 原始色阶 | `--s-nb-950:#151517` / `--s-ds-450:#5686fe` | `@deepseek-ai/dsh-client-ui-theme` 的 `--dsw-static-*` |
| 语义别名 | `--q-bg-base` / `--q-line-2` / `--q-fg-2` | 同上的 `--dsw-alias-*` |
| 高度/动效 | `--q-elev-panel` / `--q-mo-base:0.2s` | 同上的 `--dsw-elevation-*` / `--ds-transition-duration` |

好处是配色有据可查（不是"深色 + 蓝色"的即兴发挥），
且与原项目**兼容**：旧变量名（`--bg/--tx/--ac/--bd`…）在 `00-tokens.css`
里一次性映射到新色板，所以移植层里那些内联 `var(--bd)` 不用改一行。

浅色/深色两套完整覆盖，默认 `data-theme-pref="auto"` → 跟随系统。

## 三个"重构"而非"换皮"的地方

1. **外壳**：横向页签 → 左侧导航（含 60px 图标栏折叠态 + Ctrl+B）。
   导航项仍是 `#tabs .tab[data-tab]`，移植层的 `switchTab` 完全不知道结构变了。
2. **详情视图**：原来的卡片堆 → **时间轴**。每次工具调用是轴上带圆点的节点，
   按类型着色（思考=灰、已发送=绿、出错=红、结束=蓝），左侧一条 1px 竖线串起来。
3. **窗口**：`frame:false` 去掉 Windows 原生标题栏与三键，
   页面里自绘「最小化 / 最大化 / 关闭」，经 preload 的 IPC 打到主进程。

## 动效口径（统一，不是各处随手写）

| 场景 | 时长 | 缓动 |
|---|---|---|
| 悬停 / 按下 | 0.1s | `--q-ease` |
| 视图交叉淡入淡出 | 0.2s（旧视图）/ 0.3s（新视图入场） | `--q-ease-out` |
| 侧栏折叠、设置卡展开 | 0.3s | `--q-ease-out` |
| 弹窗入场 | 0.3s 缩放+位移 | `--q-ease-out` |
| 列表项入场 | 0.2s，前 5 项错峰 12ms | `--q-ease-out` |
| 状态点呼吸、骨架屏扫光 | 1.4–1.8s 循环 | `--q-ease` |

并且**尊重 `prefers-reduced-motion`**（全局兜底压到 0.001ms）。

### ⚠️ 一个必须分清的边界：页面级断言 ≠ 真实窗口

CDP 那套工具（`check-*`）会**另起一个 headless Edge** 去加载目标 URL，
所以它量到的是 Edge 的渲染结果，不是 QQ Agent 的 Electron 窗口。
两者在这些点上**必然不同**，不能互相断言：

| | headless Edge | 真实 Electron 窗口 |
|---|---|---|
| `data-shell` | `browser` | `electron` |
| `window.qqAgentShell` | 不存在 | 存在（controls / windowState / …） |
| `#q-winctl` | 被 99-shell-boot.js 移除 | 存在且可用 |
| 标题栏高度 | 48px | 40px |

- 用 CDP 验证**界面本身**（布局、样式、动效、主题、按钮行为）→ 可靠。
- 验证**真实窗口**（无边框、自绘三键、桥接）→ 用 `shot-window.mjs` 抓 OS 层像素，
  以及主进程日志（main.js 会把 renderer 的 console 转发到 stdout）。
- `which-target.mjs` 就是用来随时确认"这次测的是谁"，避免再把两者混为一谈。

## 本轮踩过的大坑（都已写成注释留在代码里）

1. **`@layer` 方向反直觉**：未分层样式 > 任何分层样式。必须用
   `@import url() layer(legacy)` 把整张旧皮肤放进低层，否则旧皮肤永远赢。
2. **CSP hash 与换行符相关**：CRLF 文件按 LF 算 hash 永远对不上，
   而失败时只有一条 console 警告。现同时放行两种形态的 hash。
3. **`ELECTRON_RUN_AS_NODE=1`**（本次最贵）：DSH 宿主设了这个变量，
   从 Agent 的 shell 里 spawn Electron 会让它**退化成普通 Node** ——
   不读 main.js、不初始化 Chromium、静默 code 0 退出，
   现象与"单实例锁没释放"一模一样。`restart-agent.mjs` 现在会显式剔除它。
4. **无头浏览器默认 `prefers-reduced-motion: reduce`**：会把所有过渡压成 0.001ms，
   让"动效"整片误判。`cdp.mjs` 已默认强制 `no-preference`。
5. **视口宽度会改变结论**：< 880px 命中侧栏窄窗口媒体查询，断言要用 1600px。
6. **ESM 的 TDZ**：模块级 `const` 在声明前使用会抛 ReferenceError（不是 undefined），
   Electron 会在写任何日志之前就退出——`check-electron-startup.mjs` 专门查这个。
7. **覆盖别人的组件前先看它的 DOM 结构**（两个 bug 的同一个根因）：
   - 我把 `.track` 当峰谷滑条的轨道写成 `height:6px; flex:1`，
     但 `.track` **被开关复用**（`<label class="switch"><span class="track">`）——
     所有开关的轨道被压成 6px 高、宽度被撑开，就是用户截图里的"开关错位"。
   - 我给 `.tier-knob` 加了 `top:50% + transform:translate(-50%,-50%)`，
     而它本来是靠 **inline `left:%`** 定位的竖条 —— 两种定位叠加，滑块飞出轨道。
   - 另外 `.ac-tier-wrap` 必须 `flex-direction: column`：
     旧代码的 DOM 是 `(滑条, 读数, 提示)` 三个兄弟，我写成默认 row 后，
     读数里那段带 `<br>` 的长描述把宽度吃光，滑条被压成 **2px**（滑块按 % 定位就飞了）。
   现已加 `tools/check-selector-scope.mjs` 扫描"裸写通用类名"，
   以及 `tools/probe-box.mjs` 看盒子尺寸，避免同类问题再靠肉眼找。

8. **`switchTab` 是唯一会建立 `.tab.active` 的地方**：启动路径原来直接调
   `loadSessions()`，于是首屏**左侧导航没有任何一项高亮**，而内容/数据全对
   （data-view / view.active / 列表都正常）——"能看能用"所以极难察觉。
   已把启动改为走 `switchTab('sessions')`，让启动与点击**同一条路径**。

9. **测量方式本身也会骗人**：
   - `.thumb` 有 `transition: transform`，改完立刻读 computedStyle 拿到的是
     **过渡当前帧**（读到改色前的值），于是"功能正常"被判成失败。
     → 要么先关动效、要么查**像素**（`check-accent-pixel.mjs` 就是干这个的）。
   - `[data-motion=off]` 把时长压到 0.001ms 后，浏览器序列化成 **`1e-06s`**，
     只匹配 `0.001ms` 会误判。
   - 无头 Edge 访问 dev-server 时，Origin 是 `:3400` 而上游是 `:3210`，
     上游的 `originAllowed()` 会回 403 —— 看起来像"设置页坏了"，
     实为开发代理的产物。`dev-server.mjs` 现在会改写 Origin/Referer。

## 2026-10-04 第三轮：用户第二次反馈

### 1. 峰谷滑条"看不到档位"（对比度）

不是布局问题，是**颜色**问题。上一版把区间底色写成 `--q-accent-soft`，
而浅色主题下那个令牌是 **12% 透明度的蓝** —— 叠在近白底上仍是近白，
于是第 4 档的蓝字压在自己的蓝底上，对比度算出来是 **1.00**（等于隐形），
第 3 档深灰字也只有 1.37，第 1 档 3.55 同样偏低。

→ 底色改成用 `color-mix` 与滑条底**混出不透明**的浅蓝/浅灰，文字统一主文字色。
现在四档最低对比度：浅色 **18.08**、深色 **17.45**（远超 WCAG AA 的 4.5）。
验证方式也换了：不再"看颜色对不对"，而是**把半透明前景合成到实际底色上再算对比度**，
并且两套主题都跑。

### 2. 活跃设置的「取消/保存」没并排

DOM 是 `class="field" style="display:flex;gap:8px"` —— 内联只给了 `display`，
**方向被 `01-base.css` 的 `.field{flex-direction:column}` 接管了**，所以两个按钮各占一行。

修法：在样式表里用 `#ac-editor .field` 把方向钉成 row，并把说明文字推到下一行。

⚠️ 我第一次写成 `.ac-editor`（**class**）—— 而 DOM 里是 `id="ac-editor"`，
选择器根本不匹配，白改一轮。这类"选择器没匹配上"的失败**没有任何报错**，
只能靠工具查：`node tools/probe-rules.mjs "<选择器>" <属性>` 会直接告诉你命中几条规则。

### 3. 主题切换：从"盖住界面"改成"界面本身扩散"

上一版是在按钮位置放一个**不透明圆**放大到铺满整屏。它确实 `pointer-events:none`
（不拦点击），但**视觉上整屏被一块颜色盖住了** —— 与用户要的
"从按钮出发、扩散到界面、不阻拦任何元素"不是一回事。

→ 改用 **View Transitions API + `clip-path` 圆形揭示**：
浏览器把切换前后各拍一张快照，我们让**新状态的界面**从按钮位置以圆展开、旧状态原地不动。
于是"扩散"的就是界面本身：**不多出任何一层颜色、任何元素都不被遮挡、
也没有任何东西被拦截**（快照层由浏览器管理且已显式声明 `pointer-events:none`）。

不支持的浏览器或关掉动效时**直接切换**——宁可没有动效，也不退回"盖住界面"。

验证的坑：**不能用 `elementFromPoint` 判断"能不能点到元素"**。
View Transition 的 `::view-transition` 是浏览器生成的顶层伪元素，
命中测试会把它（的宿主 `html`）报出来，即使 `pointer-events:none`。
判断"会不会拦截"要看 `getComputedStyle(el, '::view-transition-new(root)').pointerEvents`。

## 2026-10-04 第四轮：用户第三次反馈

### 1. 顶栏主题图标（亮色要显示太阳）

原实现按**偏好档位**选图标，于是 auto 档显示"显示器"图标 —— 系统是亮色时
用户看到的是亮色界面却配着一个显示器图标，像是没生效（用户截图即此情况）。
现在按**实际生效主题**选图标：亮色 → 太阳、暗色 → 月亮，
auto 档也一样（title 里另行说明"跟随系统"）。
两个图标共用同一套几何（`viewBox 20×20`、`stroke-width 1.6`、round 线帽），
切换时视觉重量一致。CSS 也从 `[data-pref=…]` 改为 `[data-theme=…]` 取色。

### 2. 选色界面：三种格式全部罗列

新增 `shell/12-color-format.js`（解析/互转）+ 每项三个输入框（HEX / RGB / HSL），
**同时可见、都可编辑**，填任一个就自动补齐另外两个；取色器也跟着同步。

一个必须记住的坑：**不能用 `getComputedStyle` 判断"浏览器认不认这个颜色值"**。
探针上写 `color: not-a-color` 时浏览器会**丢弃该声明**，computedStyle 于是回落到
上一个有效声明（继承值 = `rgb(0,0,0)`）—— 直接采信就会把**任何乱码解析成黑色**，
用户打错一个字颜色就被悄悄改成黑，而且会写进 localStorage。
正确判据是**哨兵色**：先设一个绝不可能撞上的值，再 `setProperty` 覆盖成用户输入，
结果仍等于哨兵 → 声明被丢弃 → 判为非法（`tools/check-color-format.mjs` 覆盖了这条）。

同时：存进 localStorage 的一律是规范化 `#rrggbb`（带 α 则 `#rrggbbaa`），
避免 hex/rgb/hsl 三种写法混在配置里；解析失败时**保留用户输入、不落库**并标红。

### 3. 卡头三件套往左 + 说明文字往右

- 控件组（峰谷时段 / 档位参数 / 统一设置）：旧皮肤写的是 `margin-right: auto`
  （空白推到右侧），但它在 `layer(legacy)` 里，被我未分层的 `margin-left: auto`
  盖掉了 —— 于是控件组被拉到最右。现在明确 `margin-right: auto`，
  同时把有 extra 的卡头里 `.sc-tt` 从 `flex: 1` 改为 `flex: 0 1 auto`
  （否则标题块会把控件组推走）。实测间距：标题→控件 **20px**，控件→摘要 **368px**。
- 「当前编辑：…」：它在 DOM 里是 `.tier-read` 的**兄弟**，用负上边距提到同一行右端。
  ⚠️ 第一版把 `.tr-txt`（说明）也设了 `margin-left:auto + text-align:right`，
  结果说明与「当前编辑」**叠在同一位置糊成一片** —— 而"同一行 + 靠右"的几何断言
  居然全都通过。所以 `tools/check-readout-layout.mjs` 专门断言**矩形不相交**。

### 4. 滑条"仍然被遮挡" —— 真凶是折叠卡内容溢出

绕了四轮才定位到，记录完整过程：

- 现象：滑条中段浮着"思考强度"的下拉框（用户截图）。
- 第一层误判：几何相交检测说 `div.field` / `select` 与滑条矩形相交，
  但 `elementFromPoint` 九点全命中滑条 —— 二者矛盾，一度以为是自己看错。
- 找到真凶：**关闭的折叠卡内容在漏出来**。
  关闭卡的 `.setcard-body` 只有 14px 高，而里面的 `.field` 是 73px：
  内容照常绘制到卡外，正好落在下面「活跃设置」的滑条区域上。
- 根因：旧皮肤靠 `grid-template-rows: 0fr` **加上**内容的 `overflow: hidden` 来裁剪；
  我把旧皮肤整张放进 `layer(legacy)` 后，**未分层样式胜过分层**，
  那条 `overflow: hidden` 输给了我写的 `.setcard-body{display:grid}`。
  于是"高度对了、内容却漏出来"——比完全不管更难查。
  期间补过 `min-height:0`、`overflow:hidden`，在这种"grid 轨道塌缩 + 子元素
  min-content"组合下裁剪行为并不稳定。
- 最终修法：关闭态**直接不渲染**（`display: none`），给展开态补一段轻微淡入。
  `display:none` 没有裁剪歧义：内容不参与布局、不绘制、不可能盖住任何东西。
  实测四张关闭卡全部 `display:none / 0px`。

**这一类的通用教训**：把旧皮肤整体降层时，凡是"靠 overflow 裁剪 / 靠层叠顺序"
才能正确工作的旧规则，新样式都必须自己重写一遍 —— 它们不会继续生效，
而且失效方式是"布局尺寸看起来正常、视觉上却是错的"。

### 顺带修掉的

- 个性化页未自定义项的色块原本是一块**灰**（看不出这项影响什么颜色），
  现在显示解析出的真实默认色；实测 12 个色点里 9 种颜色。
- `check-slider-switch` / `check-tier-buttons-theme` 两个工具都因为
  "设置页一次只渲染一个区块"而误报（量到别的区块或折叠卡内的 0×0 元素）。
  现在都会先切到目标分区再量，并断言"区块已渲染"作为量测前提。

### 关于"硬缺失 39 处"：一次差点被误导的结论

`check-dom-contract` 会报"有 N 处硬缺失，需要补"。**这个数字本身没有意义**：
新 UI 里有一批 id 只存在于旧版的模态框 / 删除确认条 / 启动遮罩中，
静态扫描必然报缺失。实测对照：

| | 静态 id 命中 | 未命中 |
|---|---|---|
| 旧控制台（baseline） | 114 / 158 | 44 |
| 新 UI | 119 / 158 | 39 |

新版未命中集是旧版未命中集的**真子集** —— 也就是说新版**没有**缺任何旧版确实存在的东西。
所以给 `check-dom-contract.mjs` 加了 `--baseline <旧控制台url>`：
它会分别扫描两套 UI，直接算"旧版有、新版没有"的差集，并把结论写成
"DOM 契约完整 / 相对旧控制台有 N 处真缺失"。没有这个对比时，工具会明确提示
"不能据此判定缺失"，避免把 39 读成"39 个功能坏了"。

配套的两条：`compare-baseline.mjs`（逐个点开全部页签取并集）报
**旧版 260 个 id 全部保留、0 丢失**；SECTIONS 数组已补上新增的 `personal` 区块，
否则新区块里的 id 不在扫描范围内。

## 2026-10-04 第五轮：「滑条依旧诡异」

用户反馈的是**峰谷双点模式**下的读数行（截图里说明两行、`当前编辑` 悬在字中间，
看着像滑条区域被糊住）。

### 根因：负边距 hack 在"两行"场景下必然算错

上一轮为了让「当前编辑：…」和读数在同一行，我把它留在 `.tier-read` **外面**，
用一个固定负上边距（`margin-top: -36px`）把它"拽"上来。这在说明**只有一行**时碰巧对，
但峰谷双点模式下说明是**两行**（高峰 / 低谷），行高变了，负边距一算不准，
它就悬在说明文字中间 —— 正是用户看到的"诡异"。

**这次不再打补丁，直接改结构**：把 `.ac-target` 移进 `.tier-read` 内，
和 `.tr-big` / `.tr-txt` 成为三个兄弟，用真正的三列 flex 排布：

```
[ 峰 1 档 · 谷 4 档 ]  [ 高峰：…/低谷：…（可换行） ]  …留白…  [ 当前编辑：… ]
```

任何行数下都不会错位，也不再依赖任何负边距。实测两种模式：
单档（说明 1 行）与峰谷双点（说明 2 行），三部分两两**矩形不相交**、
「当前编辑」始终贴最右、滑条九点命中自身、读数区无元素溢出。

### 顺带清掉两处"规则打架"

`40-market.css` 里同时存在两套读数样式，后一套把前一套覆盖了：

- `.tr-big { font-weight: 650 }` 盖掉了 `.tier-read .tr-big { font-weight: 700 }`
- `.ac-target { display: flex }` 盖掉了把它当作行内提示的设定

它们**特异性更低但位置更靠后**，所以真的生效了 —— 这种"新写的规则没生效、
但也没报错"的情况只能靠工具查（`probe-rules.mjs <选择器> <属性>` 会列出命中规则）。
现在读数样式只在 `.tier-read .tr-*` 一处定义，改起来不会再两处打架。

### 测试覆盖补强

`check-readout-layout.mjs` 现在**两种模式都跑**（单档 + 峰谷双点），
并显式断言"峰谷模式下说明确实是两行"以确认复现了问题场景 ——
上一版只在单档模式量过，所以那个负边距 bug 从断言里溜过去了。
这也是一条通用教训：**给一组断言时，要覆盖会触发不同布局的分支**，
否则"测试全绿"只说明默认分支没问题。

## 2026-10-04 第六轮：「2、3、4 档的文字依旧飞走了」

### 根因：一条"小圆点"规则误命中了档位区间

`30-settings.css` 里有一条我给**分群按钮上的小圆点**（标"该群有单独设置"）写的规则：

```css
.ac-tier-wrap .d2, .ac-tier-wrap .d3, .ac-tier-wrap .d4 { width:4px; height:4px; border-radius:50%; }
```

而档位区间的 class 正是 `tier-band d2 / d3 / d4` —— 选择器**同时命中两者**。
于是第 2/3/4 档的区间盒子被压成 **4×4 圆点**，里面的文字被
`display:flex; align-items:center` 居中到那个 4px 盒子里，
算出来 y 就到滑条**外面**去了。

第 1 档的 class 只有 `tier-band`（没有 d2/d3/d4），所以安然无恙 ——
这正好解释了"为什么只有后三档出问题"。实测证据（`probe-tier-bands.mjs`）：

```
档位 1   盒子 height=40px   文字在滑条内=true
档位 2   盒子 height=4px    文字在滑条内=false   ← 被压扁
档位 3   盒子 height=4px    文字在滑条内=false
档位 4   盒子 height=4px    文字在滑条内=false
```

### 修法与防线

1. 删掉那条规则（小圆点若还需要，必须用带前缀的专用类名，别用 `.d2` 这种通用短名）。
2. `.tier-band` 加 `height: 100% !important` —— **布局性属性不该被装饰性规则改掉**。
   只写 `top:0; bottom:0` 时，任何一条更靠后的规则只要给 `.tier-band.d2` 加个 height
   就能把它压扁，而现象（文字飞出轨道）离"原因（某处写了 height:4px）"非常远。
3. 断言补强：`check-tier-buttons-theme` 新增**几何**断言 ——
   每档盒子高度必须 ≈ 滑条高度、每档文字必须落在滑条矩形内、且 opacity/visibility 正常。
   ⚠️ 关键点：**只断言"对比度/颜色"抓不到这个 bug** ——
   文字确实渲染了、颜色也对（我当时就是这么被骗过去的），必须量几何。
4. 扫描工具扩展：`check-selector-scope.mjs` 新增**短数字类名**检测
   （`.d2` 这种"单字母+数字"的名字极易撞车），并点名优先复核。

### 一条通用教训

`d1/d2/d3/d4`、`.t1`、`.x2` 这类**单字母+数字**的类名是高风险命名：
它们看起来像"局部小标记"，但恰恰因为短，非常容易和别处的语义撞上，
而且撞上后**不报错**，只是布局悄悄变错。给组件起类名时宁长勿短
（`.ac-group-dot--has-own` 比 `.d2` 好得多）。

## 2026-10-04 第七轮：标题栏瘦身 —— 功能控件移到内容区工具栏

用户要求：标题栏里除最小化/最大化/关闭以外的按钮，全部挪到内容区顶部（原蓝框空区），
界面整体下移。

`.q-main` 本来就是 `flex-direction: column`，工具栏作为第一个 `flex: 0 0 auto`

这批控件的样式原本全写在 `#topbar …` 下（因为它们在标题栏里）。

全部退化成无样式的裸文字/裸下拉。已统一换成 `.q-main > .q-tb-status …`：

- 用 `>` 是刻意的：避免误伤内容区里同名的通用类（设置页里也有 `.btn` / `.muted`）。
- 特异性高于旧皮肤的分层规则，因此不再需要原来的 `#topbar` ID 前缀

窄窗口策略也随之放宽：原来为了把胶囊塞进 40px 高的标题栏，1020/900px 就要隐藏

## 2026-10-04 第八轮：「无痕」—— 取掉顶栏与主体之间的缝

用户要求：任务栏与主体之间不要缝，看着舒服。

### 三层接缝，两种成因

| 位置 | 成因 | 处理 |
|---|---|---|
| 标题栏 / 功能条 之间 | 各有一条 `border-bottom: 1px solid` | 两条线都删掉 |
| 功能条 / 内容区 之间 | 同上 + **底色令牌不同**（暗色下才显形） | 删线 + 统一用 `--q-bg-base` |
| 功能条左侧与侧栏交界 | 工具栏原本在 `.q-main` 里，左侧从侧栏右界开始 | 工具栏提到 `.q-body` 下、`flex: 0 0 100%`，横跨整窗 |

### 一个只有像素采样才抓得到的坑

计算样式里 `border-bottom-width` 全都是 `0px`，但**暗色下 y=92 处仍有一条
横贯整窗的色差线**。原因是底色令牌选错了：

```
--q-bg-sidebar = --s-nb-900 = #1b1b1c
--q-bg-base    = --s-nb-950 = #151517
```

两者在**浅色下恰好同值**（都是 `--s-nb-50` = #f9fafb），所以浅色主题完全看不出问题；
暗色下差 6 级明度，就露出一条线。如果只看浅色截图、或只查 border，这个 bug 会一直藏着。

→ 结论：**"有没有缝"必须用像素验证**，不能只信计算样式。
`tools/check-seamless-pixels.mjs` 就是干这个的：它自己解 PNG（zlib + 反滤波），
沿内容区空白处与窗口最右各取一条 130 行的竖线，断言**颜色变化次数 = 0**。
两套主题都跑，现在都是 `0 处`。

同时 `check-shell-toolbar` 也补了一条"标题栏与内容区同底色"的断言 ——
它比像素检查更早失败、报错更直白，两者互为补充。

### 布局结构（当前）

```
#q-shell (flex column)
├─ #topbar            flex: 0 0 auto     品牌 + 窗口三键（无下边框，底色 = 内容区）
└─ .q-body            flex: 1, wrap
   ├─ .q-tb-status    flex: 0 0 100%     功能条（横跨整窗，无下边框，同底色）

   └─ .q-main         flex: 1 1 auto     内容区
```

`.q-body` 必须 `flex-wrap: wrap`：否则工具栏、侧栏、内容区会并排成三列

它是"导航 / 内容"的结构分界，去掉会让左侧导航和内容糊在一起，反而更不舒服。

## 2026-10-04 第九轮：导航颜色连续 + 底部互动元素消失

用户反馈两点：「不是每一个导航栏的颜色都是连续的」「部分导航栏的金句上传、意见收集等
互动元素会消失」。

### 一、底部互动元素消失 —— 侧栏被内容撑到 3003px

实测（`tools/probe-height-chain.mjs`，会话页签）：

```
#q-shell         h=  900   ← 正常
.q-body          h=  852   ← 正常（容器高度没问题）
.q-sidebar       h= 3003   ← ❗ 被撑高
.q-side-foot     y 2844~3095  ← ❗ 被推到视口外（视口只有 900）
#layout          h= 3003
.view.active     h= 3003
.list-pane       h= 3003   ← 长内容，overflow: visible
```

根因是**内联尺寸反向传播**：`.list-pane` 里是长会话列表，`overflow: visible`
让它把内容高度传上去，于是一整行（`.q-sidebar` 与 `#layout`）被
`align-items: stretch` 撑到与内容等高。侧栏被撑高后，它底部那排入口
（金句上传 / 意见收集 / 市场 / 人设广场 / 打开网站）就落到了视口之外。
会话页签列表最长所以最明显 —— 这解释了用户说的「**部分**导航栏…会消失」。

**修法**：`.q-body` 从 flex-wrap 改成 **grid**。两行两列的网格正好就是这个结构：

```css
.q-body {
  display: grid;
  grid-template-columns: auto minmax(0, 1fr);   /* 侧栏 | 内容区 */
  grid-template-rows: auto minmax(0, 1fr);      /* 工具栏 | 余下 */
}
.q-body > .q-tb-status { grid-column: 1 / -1; grid-row: 1; }
.q-body > .q-sidebar   { grid-column: 1; grid-row: 2; }
.q-body > .q-main      { grid-column: 2; grid-row: 2; }
```

grid 轨道尺寸**就是可用空间**，子项默认 stretch 到自己的轨道，
不存在"被更高的兄弟撑开"这回事。修完侧栏 808px（= 852 − 44），
底部入口底边正好 y=900，9 个页签 × 2 主题全部可见可点。

中间试过 `align-items: flex-start` + `height: 100%`，结果 `height: 100%`
解析的是**整行**高度（852）而不是"剩余高度"（808），侧栏比可用空间高 44px、
底部两个按钮仍被裁掉。**flex-wrap 在这个场景下有两个互相打架的"高度"语义，
grid 没有这个歧义** —— 这是换布局的理由，不是审美偏好。

### 二、导航颜色不连续 —— 三处深浅不一

| 元素 | 原来 | 问题 |
|---|---|---|
| 侧栏 `.q-sidebar` | `--q-bg-sidebar` = `--s-nb-900` #1b1b1c | 深色下比 `--q-bg-base`(#151517) **亮一档** → 左侧是一块"比别人亮的板子" |
| 当前页签 `.tab.active` | `--q-bg-nav-active` = `--s-nb-750` 不透明填充 | 侧栏里再叠一块更亮的方块 |
| 悬停 `.tab:hover` | `--q-bg-nav-hover` = `--s-nb-850` 填充 | 又一块异色 |

### 两个"判据写窄了"的假失败

1. **无痕像素扫描把它当成了接缝**。原来我沿内容区竖线扫 0~129 行、要求全程同色；
   而新横幅就在 y=110 处（琥珀色）→ 被报成"有横向接缝"。
   改成：先问页面"这一行是不是纯外壳底色"（`elementFromPoint` + `closest('.dash-wrap, .dash-card, …')`），
   有内容的行跳过；扫描范围也收敛到**外壳层带**（标题栏 + 功能条 = 92px，

2. **颜色解析不认识 `color(srgb …)`**。`color-mix()` 算出来的颜色，

Chromium 合成时会产出 ±1 级像素差（实测暗色 x=1430 处 `rgb(21,21,23)` ↔ `rgb(21,21,24)`），

## 2026-10-04 第十二轮：标题栏「重载界面」按钮

用户要求：在标题栏 logo 旁边加个重载按钮，省得每次按 Ctrl+Shift+R。

实现：`#q-reload-btn`（24×24，与 logo 呼应）放在 `#q-tb-drag` 内、品牌区之后。
点击 → 转一圈（420ms）→ `location.reload()`。

**为什么用 `location.reload()` 而不是拉主进程做 `webContents.reload()`**：
这是**页面级**动作（刷新 DOM/样式/脚本），走渲染层最直接；也不必为它给 preload 的
`WINDOW_ACTIONS` 白名单加一项 —— 那套动作的语义是"窗口操作"，混进 reload 会模糊边界。

**为什么先播旋转再刷新**：刷新会立刻销毁页面，用户看不到任何"点到了"的反馈，
会以为按钮没反应而反复点。先转 360° 既有确认感，也不至于让人等。
关闭动效 / 系统"减弱动态效果"时**直接刷新、不延迟**（走另一分支）。

⚠️ **无边框窗口的关键点**：它在 `#q-tb-drag`（`-webkit-app-region: drag`）内部，
必须显式 `no-drag`，否则点不动。虽然已有 `#q-tb-drag > * { no-drag }` 兜底，
这条仍然单独写了一遍并纳入断言 —— 拖动热区里的交互元素是无边框窗口最经典的坑。

### 验证这个按钮时试错三次（都记在工具注释里）

| 手法 | 结果 |
|---|---|
| 劫持 `location.reload` | ❌ Chromium 里它是 **non-configurable**，报 "Cannot redefine property: reload" |
| 挂 `beforeunload` + `preventDefault` 拦住导航 | ❌ 阻止导航会把 CDP 的 `Runtime.evaluate` 一起卡住（等不到返回值，超时） |
| **不拦它，让它真的刷新**，用每次加载都重新赋值的 `window.__reloadProbe` 确认文档换过 | ✅ 最直接，也最贴近用户要的"点了会刷新" |

另外还踩了个老坑：页面代码里**不能出现 `${...}`** —— 那段是 Node 的模板字符串，
会先被当插值算掉，页面收到残缺代码报 "Unexpected end of input"。

新增工具：`check-reload-button.mjs`（13 条：位置/尺寸/可点命中/no-drag/旋转反馈/
真的重新加载/关动效时立即刷新）。

## 2026-10-04 第十三轮：把"测试偶发失败"根治掉

这一轮没有改产品功能，专门解决一件事：**批量跑套件时会出现随机失败**，
而单独重跑每个套件都是绿的。这类"偶发"最容易变成"反正重跑就好"的敷衍，
所以逐个查清了根因。一共四类：

### 1. 启动遮罩吃掉坐标点击（影响最广）

应用启动时有个 `z-index:999` 的全屏 `#loading-overlay`。
CDP 的 `page.click` 是**按坐标派发真实鼠标事件** —— 点会落在遮罩上，
页签根本没被点到，于是后面所有 `waitFor` 超时（"设置菜单/峰谷滑条 等不到"）。
看上去像功能坏了。修法：所有套件开头统一等
`!document.getElementById('loading-overlay')`。

### 2. 启动竞态：链路没走完就去操作

启动默认落在「仪表盘」，`loadDashboard()` 会发请求。在启动链路走完之前点设置页签，
会出现"`state.settingsSection` 已变成 chat，但 `#ac-editor` 还是空的"。
修法：加**启动门禁** —— 等 `#tabs .tab.active` 已建立（只有 `switchTab` 会 toggle 它，
所以它是"启动链路走到最后一步"的可靠标志）且遮罩已摘除。

### 3. 把"点了"当成"渲染完了"

`page.click` 返回只代表事件派发出去了，`renderSettings()` 可能还没跑完。
典型症状：`loadSettings()` 要拉 config + skills（1~2 秒），
固定 `sleep(1400)` 在批量跑时不够 → 报"二级菜单里没有个性化"。
修法：一律 `waitFor(目标元素)`，不用固定 sleep 猜时长。

### 4. CDP 调试端口偶发拿不到

批量跑时偶发 `CDP 端点不可用：…/json/version (fetch failed)`：
随机到的端口刚好被上一条没退干净的 Edge 占着，而 `--remote-debugging-port`
拿不到端口时浏览器**直接退出**，再 fetch 必然失败。
修法：`cdp.mjs` 里加重试（换端口 + 重启浏览器，最多 4 次）。

### 5. 批量插入脚本把代码插坏了（这条最值得记）

我用脚本批量往 21 个文件里插等待片段，插入点是"第一个 `await page.waitFor(`"。
但有的文件第一个匹配落在**辅助函数内部**（`check-theme.mjs` 的 `applyDirect`），
于是片段被插进函数体中间，还破坏了原来那行的反引号结构 ——
变成 `page.waitFor(!document....)` 这种语法错误。
**这类问题在 150 行的文件中间，肉眼 review 基本发现不了。**

→ 因此加了 `tools/audit-insertions.mjs`：专门扫"批量插入留下的痕迹"
（丢了反引号的 `waitFor(`、门禁片段被更深缩进夹在函数里）。
那条"插入位置对不对"的自检，比修好那一个文件更有价值。

### 新增：一键回归

`tools/run-all-checks.mjs` —— 依次跑全部 21 个套件并汇总，
约 5.8 分钟，输出形如：

```
✔ 无痕（像素级）    16769ms  无痕验收通过：内容区与窗口边缘全程没有横向接缝。
✔ 重载按钮          10635ms  重载按钮验收通过。
...
21/21 个套件通过（共 347 秒）
```

在这之前，"全部通过"是我手工一条条跑出来的，既慢又无法复现；
现在它是一句命令、一个可比较的数字。

### 中文字体：怎么在"拿不到游戏字体"的前提下尽量对齐

塔科夫中文界面用的是**游戏内嵌的定制字体**。我拿不到，也不该把游戏字体文件
打进这个项目（授权问题），更不该偷偷塞一个来路不明的字体。
所以做法是在**系统已有字体**里挑最接近"厚重紧凑黑体"的组合，收进一个变量：

```css
--q-font-tarkov: "Microsoft YaHei Heavy", "Source Han Sans SC Heavy",
  "Noto Sans SC Black", "Source Han Sans SC", "Noto Sans SC",
  "Microsoft YaHei", SimHei, "Heiti SC", -apple-system, …;
```

- **Microsoft YaHei Heavy**：Win10+ 自带的最重一档，最接近那种厚重感 —— 优先
- SimHei / 黑体：老系统退路，字形更方、也够重
- 思源黑体 / Noto Sans SC：装了这些的机器
- 再配 `font-weight: 800` + 略紧 `letter-spacing`，读起来是"游戏内通告"而非普通网页提示

⚠️ 如果以后拿到**有权使用的**更接近的字体：`@font-face` 之后把名字加到
`--q-font-tarkov` 最前面即可 —— **接入点就是这一个变量**，结构与其它的样式都不用动。

### 顺带把对比度做上去了

## 2026-10-04 第十六轮：宋体发虚 + 徽章再放大

用户反馈"中文字体有点糊"、"感叹号和六边形都再大一点"。

### 宋体发虚的根因：非整数栅格化

宋体（SimSun）是**点阵字体** —— 它内嵌位图字形，只在"设备像素正好等于字号"时最锐利。
一旦出现非整数缩放或子像素偏移，浏览器就得反锯齿，整条字立刻发虚。

实测（`tools/probe-font-sharpness.mjs` 出一张并排对比图，8 个字号同屏渲染）：
在 dpr=1 下 **20px / 21px 明显比 19px / 22px 锐**，与上面的判断一致。

修法（都写进注释了）：
- `font-size` 与 `line-height` 一律用**整数 px**（21/30、15/22），不写 18.5 这种
- 给文字加 `transform: translateZ(0)`，提到独立合成层、避开子像素定位
- 关掉 `font-kerning` / `font-variant-ligatures`（宋体本来就用不到）
- **去掉 `opacity: 0.92`** —— 半透明会让宋体本来就细的笔画更糊；
  层次改用略浅的实色（`#241a09`）表达

顺带把字号从 19/14 抬到 **21/15** —— 宋体在 14px 这个级别又小又细，
配合整数缩放一起解决"糊"的观感。

### 徽章 34 → 46 → 58px

用户两次要求放大。58px 是按"与两行文字总高相当（30+2+22=54px）"定的，
比例上才是"一个图标配两行字"，与原图一致。

### 一个测量工具本身的教训：锐度不能用"强边缘占比"衡量

我先前写了个指标想客观量化清晰度（统计边缘梯度），结果显示"字号越大越锐"——
**这个结论是错的**：字号越大，笔画边缘的像素总数越少，强梯度占比自然升高，
它测的其实是**笔画粗细**而不是**模糊程度**。

真正可信的判据是**并排同屏看**（同一张图里 8 个字号一起渲染），
以及**放大到设备像素层看**（`tools/shoot-beta-zoom.mjs` 把 DPR 提到 3 再截图）。

⚠️ 这里还踩了一个坑：CDP 的 `screenshot({clip})` 在这套封装里**不生效**
（出来还是整屏）。要放大看细节，正确做法是 `Emulation.setDeviceMetricsOverride`
提高 `deviceScaleFactor` —— 它让浏览器**按更高 DPR 重新栅格化字体**，
反映的是真实的栅格化质量；而"截小图再插值放大"只是把已有像素拉大，什么都看不出来。

### 骨架屏断言也修了（又一次"断言耦合时序"）

`check-dashboard` 里"加载中有骨架"原来是"门禁过了 → 等 3 秒 → 看有没有骨架"。
但骨架是否存在取决于**数据回来得快不快**：热缓存时 300ms 就渲染完了，
于是这条在"批量跑套件"（页面已热）时失败、单独跑（页面冷）时通过。

修法：不再"等一会儿再看"，而是在**同一轮事件循环内连采 3 帧**
（`dashData = null; loadDashboard({force:true})` 后立刻 snap + rAF + 120ms），
只要有一帧见到骨架即可。现在无论后端快慢都稳定：实测 `[true,true,true]`。

## 2026-10-04 第十八轮：SnowLuma「运行日志」全是"暂无日志"

用户反馈：SnowLuma 页的运行日志全是"暂无"。

### 结论：不是这次 UI 重构改坏的

`03-snowluma.js` 与老控制台**逐字节相同**（都是 18036 字节），前端逻辑没动过。
问题在**数据源**：`/api/snowluma/logs` 返回 `{"logs":[]}`。
但同一页的「应用日志」框有 65 条 —— 所以不是"整个页面打不开"，
而是**只有"运行日志"这一个框是空的**。

### 根因

后端的 `snowlumaLogs` 是一个**内存环形缓冲**，只捕获**由本进程 spawn 的**
SnowLuma 的 stdout/stderr。而实际场景里 SnowLuma 往往是独立启动的：

- 由便携 QQ 拉起；
- 或者上次 QQ Agent 退出后它继续在跑，这次重启的 Agent 并没有 spawn 它。

这两种情况下内存缓冲永远是空的 → 面板恒显示"暂无日志"。
**但磁盘上其实有真实日志**：`<snowluma>/logs/snowluma-YYYY-MM-DD.log`，
当天那个文件已经 20 MB 且在持续写入。

### 修法（后端 `src/routes.js`，已备份）

`/api/snowluma/logs`：内存缓冲为空时，回退读当天日志文件的**尾部 400 行**，
返回 `{ logs, source }`（`memory` / `file` / `none` / `error`）。
顺带补两个细节：

- **只读尾部**：文件能到几十 MB（10-03 那天 48 MB），整读再 split 会吃掉几百 MB
  内存并长时间占用事件循环 —— 而这个接口会被反复轮询。实现按 64KB 分块从文件尾
  往前读，凑够行数就停（实测 **11ms**）。截断读取时首行通常是半行，丢掉。
- **日期回退**：当天文件不存在时（跨零点或当天还没写）往前找最近 4 天。

### UI 侧的两处改动（这次真正属于新 UI 的部分）

1. **标明来源**：标题后面加 `· 来自日志文件 snowluma-2026-10-04.log`
   （或 `· 实时输出`）。不加的话用户没法分辨"真的没日志"和"日志在文件里"。
2. **修掉时间戳重复**：从文件读来的行本来就带 `11:48:33 OK ...`，
   再前缀一个 `[HH:MM:SS]` 会变成 `[11:48:33] 11:48:33 OK ...`。
   现在只在行首没有时间戳时才补前缀。
   顺手把 `refreshSnowlumaLogs()` 与 `loadSnowlumaPage()` 里**两份重复的**
   格式化代码合并成一个 `fmtLogLine()` —— 两份实现最容易出现
   "点刷新是一个样、SSE 推来一条又变另一个样"这种诡异现象。

### 顺带修了一个"永远空白且不报错"的隐患

排查中发现后端有些接口在冷启动时会卡 3~6 秒（Windows 进程枚举、
`Promise.allSettled` 里每项 3 秒超时、外网更新检查）。
而 `api()` **没有任何超时** → 依赖这些接口的页面会一直空白、且不抛错，
控制台干净得像没问题 —— 这正是"打不开但查不出错"的典型形态。

现在 `api()` 加了 15 秒 `AbortController` 超时，并把超时区分成
`TimeoutError`（带 `timeout: true`），让调用方能给出"请求超时"这种可操作的说法。
同时 `loadSnowlumaPage` 的 catch 从"静默 console.error"改成
**页面上给出可点重试的失败提示** —— 失败必须可见。

新增验收：`check-snowluma-logs.mjs`（11 条），已并入一键回归（现 22 个套件）。

## 2026-10-04 第十九轮：SnowLuma 日志实时滚动

上一轮修完"暂无日志"后，日志是**静态**的（进页面/点刷新才重读文件）。
用户要求"让新日志实时滚出来"。

### 关键发现：SSE 通道本来就有，缺的是"事件源"

排查发现基础设施全都现成、而且前端**早就**订阅了：

- 后端有 `emit()` + `/api/events`（SSE，带 15 秒心跳与半开连接清理）
- 前端 `02-sse-sessions.js` 早已 `addEventListener('snowluma-log', …)`

问题在**没人触发那个事件**：`pushSnowlumaLog()` 只被"由本进程 spawn 的
SnowLuma 的 stdout/stderr"调用（`child.stdout.on('data', …)`）。
而用户的 SnowLuma 是**独立启动**的（便携 QQ 拉起 / 上次退出后仍在跑），
所以 `pushSnowlumaLog` 一次都没被调用过 → `emit` 一次都没发过 → 前端永远收不到。

### 修法：后端加一个"日志文件跟随器"

在 `!snowlumaProc`（即不是内置模式）时，每 1 秒读一次
`<snowluma>/logs/snowluma-YYYY-MM-DD.log` 从 `snowlumaFollowPos` 到文件尾的**新增字节**，
把完整行喂进 `pushSnowlumaLog` —— 于是原有的 SSE 通道、内存缓冲、
前端渲染全部自动生效，**没有新增任何接口或协议**。

几个必须处理的细节（都写在代码注释里）：

- **只跟随，不重推历史**：首次 tick 只把 `pos` 定位到文件尾，
  不推送已有内容（历史由 `/api/snowluma/logs` 的首屏读取负责）。
  否则挂起几小时后一跟进会把几万行灌进内存与 SSE。
- **单次上限 256KB**：防止长时间挂起后一次性读爆。
- **半行处理**：文件按行追加，读取末尾很可能截到半行 →
  存进 `snowlumaFollowPartial` 留到下次拼接，否则会出现"半截行"。
- **跨零点/轮转**：文件变了或变小了，只重新定位、不推送。
- **与内置模式互斥**：`if (snowlumaProc)` 时直接停手并清空游标 ——
  内置模式下 stdout 已被直接捕获，再跟文件就是**重复两份**。
- **生命周期**：`start()` 里启动、`stop()` 里 `stopSnowlumaFollow()`
  （否则 stop() 之后仍每秒读文件）。

### 前端：从"全量重拉"改成"追加一行"

`02-sse-sessions.js` 里的 `snowluma-log` 处理原本是
`if (appReady && state.tab==='snowluma') refreshSnowlumaLogs()` ——
即**每来一条就重新拉 400 行并整块替换 textContent**。
SnowLuma 一秒能产生几十行，于是每秒几十次 HTTP + 整块替换，
既浪费又把用户正在往上翻的历史反复重置。

改成 `appendSnowlumaLog(d)`：只在末尾粘一行、超过 500 行裁掉头部，
并按"点击前是否贴底"决定要不要跟滚 —— **往上翻历史时绝不把用户拽回底部**。

### 验证（`check-snowluma-live.mjs`，7 条）

- 独立开一个 EventSource，25 秒内确实收到 `snowluma-log`（实测 13~16 条）
- 进入页面后 20 秒内日志行数**自动增长**（实测 200 → 205 行）
- 贴底时自动跟滚
- 行数上限受控
- 用户翻到顶部后 12 秒内**不被拽回底部**（`scrollTop` 保持 0）

### 这轮又踩了两个"测试自己的坑"，都值得记

1. **`data-motion` 的开关有两个真相源**。我为了让按钮走"立即刷新"分支，
   直接 `setAttribute('data-motion','off')` —— 但 `localStorage['qqa-motion']`
   还是 `'on'`，而 SSE 触发的 quiet 重建会重跑 `motionRuntime.apply(getPref())`，
   把属性**还原成 on**。于是处理函数读到 on、进了旋转分支，
   我一度以为"实现有 bug"，其实**实现完全正确**（属性与存储不一致时以存储为准）。
   正确做法是走 `window.qqaMotion.setPref('off')`。

   → 教训：**有两处状态表达同一件事时，测试必须改"权威那一处"**，
     改派生的那处会被下一次同步覆盖，表现出来就像功能坏了。

2. **`is-spinning` 是上一次点击的残留类**。测试里"点 → 观察类名 → 真刷新"，
   而刷新前那个类没被清掉；下次进入同一文档时 `classList.contains('is-spinning')`
   读到的还是 true。修法：点击前显式 `classList.remove('is-spinning')`，
   并同时输出"点前=false / 处理函数看到的属性 / 结果"，让证据完整。

顺带修了 `check-markets.mjs` 的同类问题：skills 页固定 `sleep(1500)` 等渲染，
批量回归时 `/api/skills`（90KB+）还没回来 → 假失败"卡片 0 个"。改成等元素。

一键回归现为 **23 个套件**（新增"SnowLuma 实时滚动"），全绿。

### ② 位置游走的根因：`auto-fit` 会按可用宽度改列数

原实现：

```css
grid-template-columns: repeat(auto-fit, minmax(232px, 1fr));
```

`auto-fit` 是**响应式**的 —— 可用宽度一变，列数、每张卡的宽度、位置全都重排。
用户要的恰恰相反：他要能按"第几个格子"定位，好往里加/删元素。

改成**显式列数**：第一排 `repeat(5, minmax(0,1fr))`、第二排 `repeat(3, ...)`，
只在真的放不下时才降列（900px 以下 3 列、620px 以下 2 列）。
两排必须分开写：共用一条 auto-fit 时，第二排只有 3 个元素会被 auto-fit 摊满，
与第一排的列宽对不齐。

验证方式：在 1600 / 1180 / 1000 三档宽度下量每张卡的 `(row, col)`，
要求三档完全一致 —— 实测三档都是 `0,0;0,1;0,2;0,3;0,4`。

### ③ 跳转 + 高亮：难点在"目标页是异步渲染的"

`switchTab('usage')` 之后，`loadUsageView` 会先画骨架 → 拉数据 → 才写真实内容。
在 `switchTab` 里直接高亮必然落空（元素还不存在）。

所以分两步：`requestHighlight(target)` 先**记下意图**，
目标页渲染完成后调 `flushHighlight()` 消费。

给区块加**稳定选择器**：用量页每张指标卡带 `data-card="runs|cost|prompt|completion|rate|search"`。
**刻意不用 `:nth-child(n)`** —— 卡片顺序将来会调整，nth-child 会静默指错区块。
这也正好呼应了用户"我要好删改元素"的诉求。

映射关系（一张仪表盘卡 → 一个或多个用量区块）：

| 仪表盘卡 | 高亮目标 |
|---|---|
| 调用次数 | `runs` |
| 估算成本 | `cost` |
| Token 总量 | `prompt` **+** `completion` |
| 缓存命中率 | `rate` |
| 联网搜索 | `search` |

### 踩到的三个真实问题

1. **`pendingHighlight` 用单值存会互相覆盖**。点「Token 总量」时连续
   `requestHighlight('prompt')` 与 `requestHighlight('completion')`，
   后者把前者覆盖掉 → 实测只亮了一张卡。
   改成 `Set` 累积、`flushHighlight` 只移除**已命中**的目标（未命中的留着等下一轮）。

2. **顺手补了「输出 token」卡**。原来"输出"只作为"输入 token"卡的副标题存在，
   于是「Token 总量」点进来只能高亮一半 —— 那半边是误导。所以把输出拆成独立卡
   （用量页从 5 张变 6 张），并接上 setter。

3. **动画时长必须由 JS 算、同时喂给 CSS 与定时器**。CSS 写一份时长、
   JS 再写一份"多久之后摘类"，两者必然漂移。现在 `flashDurationMs()` 读 `--q-mo-*`
   算是，写进 `--q-flash-ms` 并用于 `setTimeout`，保证"动画结束"与"摘类"一致。
   闪烁次数做成令牌 `--q-flash-count: 2`（一处可调）。

**关动效时不是关掉功能**：关掉动效后动画会塌成 0.001ms 等于没有，
所以 `html[data-motion='off']` 与 `prefers-reduced-motion` 下改成**静态高亮**
（强调描边 + 浅底 + 光圈），靠 JS 的定时器摘掉 —— 用户仍然能看到"看这里"，只是不闪。

## 2026-10-04 第二十二轮：悬停提示四项修正 + 抓到一个真实的加载竞态

用户提了四件事：

1. 悬停窗口里成本不要 4 位小数
2. 顶点的判定严格一些
3. 悬停窗口要有轻动效
4. 悬停窗口出现的位置会遮挡曲线

### ① 成本统一两位小数

`fmtYuan` 原来对小于 1 元的值用 `toFixed(4)`（`¥0.4370`），理由是"两位会丢量级"。
但 `¥0.44` 本来就是正常的人民币表达，4 位小数在界面上更像精度暴露。
改成**统一两位**，并保留可选参数 `precision` 给确实需要精细的地方。

这个改动是**全局**的（用量页表格、卡片、排行、悬停都走同一个函数），
所以顺带把整个界面的人民币口径统一了。

### ② 顶点判定：整高竖带 → 顶点附近的小方块

上一版命中区是 `26 × plotH`（整条竖带）。好处是不用对准，但副作用是
**在这条竖线的任意高度都会触发** —— 用户反馈判定太松。

改成顶点周围的 `26 × 26` 方块。取这个尺寸的依据：圆点半径 2.6 + 容易点中的余量；
再小会退化成"原生 title 让人以为没反应"，再大就又是整条带。

### ③④ 提示框位置与动效（这两件是同一处）

原来位置固定 `top: 6px`（贴图表顶部）。顶点若在图的上半部分，
提示框正好**压住曲线本身** —— 用户要看的就是"这个点在哪"，盖住等于白看。

改成相对于顶点算位置：**优先放顶点上方，上方放不下就放下方**，都不行才夹取。
再补一个指向顶点的小箭头（`::after` + `rotate(45deg)`），
让"这个框说的是哪个点"一目了然。

动效：`opacity` + `transform` 过渡（淡入 + 轻微上浮/缩放）。
位移方向随"在上方还是下方"反过来 —— 看起来总是"从顶点那一侧冒出来"。
⚠️ 为了能做过渡，必须放弃 `display: none → block` 的切换（display 不可过渡），
改用常驻 DOM + `opacity` / `visibility`。

坐标换算有个坑：SVG 用 `viewBox` 且 `preserveAspectRatio="none"`，
x/y 两个方向的缩放比例**不同**，必须分别按 `box.width/vb.width` 与
`box.height/vb.height` 换算，不能共用一个比例。

### 顺带抓到一个**真实的**加载竞态（不是测试问题）

批量回归时 `check-dashboard` 报"5 张卡 / 0 个数据点 / 没有刷新按钮"——
**这是真 bug**：`loadDashboard()` 没有 in-flight 守卫。
测试里"触发一次强制重载看骨架"会清空 `dashData` 并重新请求，
而启动时那次加载可能同时在飞；**先发的后到**就会把结果覆盖掉，
页面直接停在骨架态（数字全是占位条）。

修法：加 `dashLoadToken` 序号，只认最后一次加载的结果
（用量页早有同类守卫 `usageLoadToken`，这里对齐）。
加完之后该套件连续 3 次单独跑 + 批量跑都稳定。

→ 这一条值得记：**"只在批量跑时失败"不等于"测试的问题"**。
这次就是测试把一个真实的并发缺陷暴露出来了 —— 如果当时当成 flaky 忽略，
用户点刷新时偶发的"页面卡在骨架"就会一直留着。

### 又把两条断言改成"不依赖时序"

1. SnowLuma 实时滚动原来断言"20 秒内**行数增长**"。但内存缓冲上限 500 行、
   前端也裁到 500 行，**打满之后行数恒定**、只有内容在滚 ——
   日志量大的机器上这条必然失败，而功能完全正常。
   改判**末行是否变化**（内容推进的直接证据）。
2. SnowLuma 日志接口的耗时阈值 2000ms → 4000ms。实测常态 11~40ms、
   批量跑偶尔因磁盘争用到 2.4s；阈值放宽仍能抓住"整读几十 MB"那种病态实现。

新增验收 `check-tooltip-fixes.mjs`（14 条），一键回归现为 **26 个套件**，全绿。

仪表盘加载竞态 —— **都是从"测试失败"里挖出来的，不是靠猜**。

### ③ 本轮抓到的三个真实缺陷

### ② 日志折叠：折叠 = **只渲染 5 行**，不是"限高 + overflow"

这是本轮唯一的设计决策点，选了后者会踩坑：

| 方案 | 结果 |
|---|---|
| CSS 限高 + `overflow:hidden` | 用户以为日志只有那几行、而且滚不动（视觉上像卡住）；还会与已有的 `max-height:320px + overflow:auto` 打架 |
| **只渲染最近 5 行**（采用） | 语义清晰 —— "折叠态就是看最近几条"；展开时给全量，两者是同一份数据切不同长度，不丢内容 |

实现要点：

- `slLogCollapsed(which)` / `setSlLogCollapsed(which, v)`：状态存 **localStorage**
  （`qqa-sl-log-open` / `qqa-app-log-open`），因为这是**用户偏好**、要跨刷新保留；
  放 `state` 里一刷新就丢。
- `slTrimLogTail(text, limit)`：保留**末尾** N 行（最近的那几行）。

  实测：连续追加 12 条后仍是 5 行。
- 折叠/展开走**整页重建**（`loadSnowlumaPage`）：因为差别是"渲染多少行"，
  切 CSS 类做不到（除非限高）。重建顺便更新标题栏的"显示 N / 共 M 行"计数。
- **标题栏显示计数**（如「5 / 53 行」）：折叠后只有 5 行，不给总数会让用户以为日志丢了。
  展开态只显示「53 行」。
- 箭头方向表达状态：折叠时 `rotate(-90deg)` 朝右（"点开"），展开时朝下（"收起"）；

## 2026-10-05 第二十六轮：Beta 通告钉在 dashboard 顶部

用户："Beta测试的提示帮我钉在原位，无论在 dashboard 怎么滑动都无法改变位置"。

### 实现：为什么选 sticky，以及锚点为什么是 -18px

滚动容器就是 `#dashboard-page`（它同时是 `.dash-pane`，`overflow-y:auto`），
通告原本是它内部 `.dash-wrap` 的第一个子元素，所以会跟着滚。

两个方案：

| 方案 | 结论 |
|---|---|
| 挪到滚动容器**外**，做成 view 级固定头部 | 看着更"钉死"，但 `renderDashboard()` 每次刷新会重写 `#dashboard-page` 的**整个** innerHTML —— 放外面的节点头一次刷新就没了，必须额外拆容器并改 JS 渲染流程 |
| **`position: sticky`**（采用） | 语义就是"滚到边界就钉住"，零 JS、且在每次重写的那段 HTML 里，不会被刷掉 |

**锚点 `top: -18px` 的由来**：sticky 的 `top` 是相对**滚动容器的 padding box** 计算的，
而 `.dash-pane` 有 `padding: 18px 20px 26px`。写 `top: 0` 会让通告停在"上内边距 18px 之下"、
露出一条缝；写 `-18px` 正好抵消，钉住时与可视区顶边齐平。

前提：祖先 `.dash-wrap` 必须保持 `overflow: visible`（实测它是），否则 sticky 失效。

### 钉住态用 IntersectionObserver + 哨兵元素判断

只在**真正钉住**时加投影（`.is-pinned`）：静止时投影是多余装饰；钉住时内容从下面滚过去，
没有投影会显得卡片"糊"在通告上。

判断方式踩了一个坑：**不能靠 `getBoundingClientRect().top`** —— sticky 钉住前后这个值
是同一个（那正是 sticky 的作用），拿它当判据必然误判。改用**哨兵元素 + IO**：
在通告**之前**插一个 1px 的 `.dash-beta-sentinel`，它滚出视野 ⇔ 通告已贴顶。

⚠️ 哨兵不能用 `visibility: hidden`：**被隐藏的元素 IntersectionObserver 不报告交叉**，
实测 `is-intersecting` 恒为 false、钉住态永远加不上。改用 `opacity: 0 + pointer-events: none`。

同时 `bindBetaPin` 在 `dashSkeleton()` 之后也调一次 —— 骨架里也有通告，
接口慢、页面停在骨架的那段时间同样需要正确的钉住态。

### ⚠️ 本轮最重要的教训：在规则块中间插新规则

给 `.dash-beta` 加 sticky 时，我把新的 `.dash-beta-sentinel { }` 规则
**插进了 `.dash-beta { }` 的中间**。浏览器**不报错**，只是：

1. `.dash-beta` 后半段（`display:flex` / `justify-content` / `padding` …）变成**孤儿声明**，
   被静默丢弃 → 通告内边距消失、徽章与文字从"左右排布"塌成"上下堆叠"；
2. 紧随其后的 `.dash-beta-inner` 被解析成 `.dash-beta-sentinel .dash-beta-inner`
   （后代选择器）→ `display` 计算值退回 `block`。

排查过程很绕：`check-dashboard-beta` 报"徽章 x 551 ≮ 文字 x 551"，
我第一反应是居中逻辑坏了，先误删过一次 `justify-content`，
直到 dump `getComputedStyle` 发现 `.dash-beta-inner` 竟然是 `block`
（而源文件里明明写着 `display:flex`），才意识到是**选择器边界**问题。

**同一类错误我在 `30-settings.css` 里也留过一处**（改 `#settings-form h3` 时的残留
`margin: 0 0 4px; }`），是同一个检查扫出来的。

### 因此新增：`check-css-structure.mjs`（静态检查，不需要浏览器）

扫描所有样式表，找"规则外的声明"与未闭合的块。两个必须避开的坑：

1. **不能直接数 `{` / `}`** —— 注释里的花括号（本仓库注释里就写过 CSS 片段）会算进去，
   得出"括号不平衡"的错误结论。必须逐字符扫描并跳过注释与字符串。
2. **不能把深度 0 出现的任何 `xxx:` 都当孤儿** —— `@import url(...) layer(...)`
   这类 at-rule 天然带冒号且合法。遇到 `@` 开头的语句整条跳过。

自检过正反两面：故意在规则块中间插一条规则的坏文件能被抓到；
注释含花括号 + `@import ... layer(...)` 的好文件不误报。
放在一键回归的**最前面**（95ms、无需浏览器），因为在写代码阶段就该拦住。

新增验收 `check-beta-pin.mjs`（9 条）与 `check-css-structure.mjs`，
一键回归现为 **31 个套件**，440 秒全绿。

### ① 区间选择器：顺手挖出一个"口径错位"的老 bug

原来标题那个胶囊显示的 `rangeLabel` 是后端回显，而请求写死的是
`/api/usage/stats?range=30d`。看着像"最近 7 天"，我一直以为是后端默认值的问题。

**实际上后端只认 `today / 24h / all / 1..30` 的数字**，它的解析是：

```js
const n = Math.min(30, Math.max(1, Number(s) || 7));   // Number('30d') === NaN → || 7 → 7
```

于是 `range=30d` 被**静默回落成 7 天**。直接问接口验证：

```
range=30d  →  range: "30d"   rangeLabel: "最近 7 天"   mode: days
```

请求参数原样回显、标签却是 7 天 —— 这就是"标题说 30 天、数据其实是 7 天"的口径错位。
用户现在要求可选，正好把这个隐性问题一并修掉。

改动：

- 新增 `DASH_RANGES`（`today / 7 / 30 / all`），**值**与后端 `resolveRange` 及用量页
  `USAGE_RANGES` 对齐 —— 两页口径必须同源，否则用户会发现"同样选 30 天，两页数字不一样"。
  （但没直接复用 `USAGE_RANGES` 常量本身：那是用量页的选择器语义，绑死会互相牵制。）
- 选择写入 `localStorage['qqa-dash-range']`（用户偏好，跨刷新保留；默认 `7`）。
- `loadDashboard` 把 range 传进 **stats 与 breakdown 两个接口**（模型占比、会话排行都来自
  breakdown，只传一个会出现"卡片是新区间、图表还是旧区间"的错位）。
- 点击时**必须清 `dashData`**：不清的话 `loadDashboard` 会在 `if (!force && dashData)`
  处直接复用旧数据重绘一遍 —— 看起来"点了没反应"。
- `.dash-wrap` 加 `data-range` 属性记录当次渲染用的区间。这**不只是给测试用的**：
  它让"当前页面上的数据是哪个区间"成为可断言的事实。

样式上做成**分段控件**（连体、相邻细分隔线）而不是四颗独立按钮：
互斥选择用连体样式更直观。选中态用 `.is-on` 而不是 `btn-primary`（后者在别处语义不同）。

### ② 侧栏：放大"组间"，不动"组内"

```

为什么要分开调：如果连组内一起放大，整列变成均匀排布、**分组的视觉边界反而消失**。
分类的"成组感"来自"组内紧、组间松"这个**对比**，不是绝对间距。

### ③ 两条"写死期望值"的断言又红了

1. `check-sidebar-regroup` 里 `组间距收紧到 ≤6px` —— 那是**上一轮**的需求

   `组间 > 组内`、`组间 ≥ 组内的 3 倍`、`组间 ≤ 项高的一半`。
   这样以后无论用户想调松还是调紧都不会误报 —— 因为真正稳定的需求是

```
<html data-skin="default|minecraft"   ← 皮肤：换配色体系 + 图标 + 字体 + 背景 + 音效

```

- **皮肤**由 `shell/01-skin.js` 负责（新文件），存 `localStorage['qqa-skin']`。
- **亮度**仍由 `00-theme.js` 负责，不改语义。
- Minecraft 皮肤的亮暗**自己定义**：`html[data-skin='minecraft'][data-theme='light']`
  与 `[dark]` 各一套变量。这样"MC 主题跟随系统明暗"也能成立 ——
  用户选 MC 皮肤后把亮度选"跟随系统"，白天是 MC 亮色、晚上是 MC 暗色。

那个文件的注释已经写明它存在的理由是"**主题是新 UI 的需求，与移植层分开**"，
而皮肤是**又一层**概念（配色体系）。混进同一个函数会让"亮度循环切换"的逻辑
（`cycleTheme` 那套跳过空转档的处理）变复杂，且两者存储 key 不同、
生命周期也不同（亮度可能跟随系统自动变，皮肤只会被用户手动改）。

### ① 音效：为什么能"合成出 MC 的味道"

MC 的 UI 音效本质上都是**几十到两百毫秒的短脉冲**，以三类成分为主：
木质敲击（带腔体共鸣）、石质干击（无共鸣的高频噪声）、机械气动。
`gen-mc-sfx.mjs` 用四个基元组合出这六种：

- `knock(dur, freq)` —— 噪声脉冲经两级低通 + 一级高通拼出粗糙带通。中心频率决定"木/石"。
- `tone(dur, f0)` —— 正弦 + 指数衰减，做腔体共鸣与音符盒。
- `whoosh(f0→f1)` —— 扫频噪声，做活塞气动。
- `creak()` —— 窄带噪声加抖动，做拉杆摩擦。

实测听感对应：`menu` 木头点击（880Hz 带通 + 196/294Hz 共鸣）、
`stone` 干击（1900/2600Hz、衰减更快）、`note` F#4 竖琴音色（基频 + 两个谐波 + 拨弦噪声）、
`piston` 扫频 420→80Hz + 150ms 处一记限位敲击。

**为什么用 WAV 不用 ogg/mp3**：那两个需要编码器。WAV 只要写 44 字节头，
浏览器原生支持——六个音效 95KB，比一张背景图还小，不值得为体积引入编码依赖。

**播放用 WebAudio 而不是 `<audio>`**，三个理由写在 `02-mc-theme.js` 里：
延迟（AudioBufferSourceNode <10ms）、可叠加（连点不互相打断）、音量（一个 GainNode 全局生效）。

### ② 背景图：低分辨率像素画 + 整数倍最近邻放大

这是"高清截图"在无法下载素材时的**可行等价物**，而且不是权宜之计——
MC 的世界本身就是方块构成的：

1. 在 **384×216** 上作画（一像素约等于一个方块列）；
2. **5 倍最近邻放大**到 1920×1080 → 每个逻辑像素变成 5×5 硬边色块。

直接在 1920×1080 上画平滑图形反而会得到一张"普通插画"，不像 MC。
色板取自 MC 方块的真实颜色（草 `#7cb04a`、泥土 `#866043`、石头 `#808080` …），
并做 ±3 的按逻辑像素抖动 —— 贴合"方块表面本来就有噪点"的观感。

**五张场景**：平原日出 / 夜晚星空 / 洞穴火把 / 森林湖泊 / 台地峡谷。
PNG 编码器自己写（Node 内置 zlib + 20 行 CRC32）——
本项目没有图片库，而 PNG 的最小实现比 JPEG 简单一个数量级，
且**无损**（像素画最怕有损压缩产生的彩色噪点破坏硬边）。

构图改了三轮才像：**地平线必须压到画面底部（约 85%）**。
第一版放在 60% 处 → 前景泥土占了 40% 屏幕，像"贴地特写"而不是 MC 截图。
配套：天空渐变要分两段（地平线附近才混暖色），否则整屏发灰。

### ③ 图标："不沿用、也不重绘"的客观判据

用户要求"全新图标，不准用现有图标，也不可以按照旧图标重绘"。
怎么才算"新设计"而不是"重绘"？**换一套几何语言**：

| | 现有图标 | MC 图标集 |
|---|---|---|
| 画法 | `stroke` 线稿 | **纯填充矩形** |
| 曲线元素 | circle / 弧线 path | **0 个** |
| viewBox | 20×20 | **16×16 像素网格** |
| 尺寸规则 | 靠 CSS 缩放 | `shape-rendering: crispEdges` 硬边 |

两者在实现层面没有任何共用几何 —— 这是可断言的（测试就是在数 `rect` 与 `curve` 的个数）。
九个图标各自对应一个真实存在的 MC 物品：工作台 / 成书 / 箱子 / 附魔书 / 红石比较器 /
工作台网格 / 红石中继器 / 玩家头颅 / 石座拉杆；品牌 logo 是**草方块**。

### ④ 拉杆开关：不改 DOM，只用 CSS 换外观

需求"开关功能采用拉杆"。做法是把 `input[type=checkbox]` 用
`appearance:none` + 两个伪元素（底板 + 木杆）画成拉杆。
**不换 DOM 的意义**：所有既有逻辑（change 事件、checked 状态、label 关联、
键盘可达性）全部照旧，零风险。开态底板透出红石橙光，杆身 `rotate(±38deg)`。

### ⑤ 字体：@font-face + font-display: swap

15.4MB 的 TTF 首次加载需要时间。用 `swap` 让文字先用系统字体渲染、
字体到位后自动替换——而不是 `block`（那段等待期整屏无字）。
字体链带三级兜底，文件缺失也不会变豆腐块。

选这份字体而不是 `Minecraft-1.ttf`（仅拉丁 14KB）的原因：
它**同时覆盖中英文**，所以界面里大量的中英混排（如 "OneBot（SnowLuma）"）
不会出现"英文像素体、中文掉回雅黑"的割裂。

### ① 字体乱码：**打了包的那份字体的 ASCII 标点字形是坏的**

            Archive i Memory           ← 斜杠画成了 i

```

结论：`[苦力怕论坛]Minecraft(同时支持中英文).ttf`（15.4MB）的
**ASCII 标点字形本身是坏的**（`:`→`u`、`(`→`C`、`/`→`i`、`¥`→折线块），
而它的**汉字部分完全正常** —— 所以"存档/记忆"里的**全角**冒号（`：`）没问题。

而系统里另有一份 `Minecraft-1.ttf`（注册名 "Minecraft"，**仅 14KB**），
ASCII 标点完全正确、字形更干净，只是没有中文。

**修法：两份都用，各管一段。**

| 字体 | 负责 |
|---|---|
| `minecraft-latin.ttf`（14KB） | ASCII、货币 ¥€£¢、数学 ±×÷≤≥≈、箭头、**全角标点** |
| `minecraft-ae.ttf`（15.4MB，`unicode-range` 限定汉字区） | 汉字 / 扩展A / 兼容汉字 |

靠 `font-family` 的字形级回退 + CJK 那份上的 `unicode-range` 自动分流，
零 JS 参与。**顺序不能颠倒**：把 CJK 那份放前面，ASCII 与全角标点就变回坏字形。

实测依据是两张对照图（`probe-font-symbols.mjs` / `probe-font-fullwidth.mjs`）：
拉丁字体把 `：（）「」、` 画得**又对又是方块像素体**，而 CJK 那份把这些画成缺角方块。
所以全角标点也必须归拉丁 —— 这一条只有看图才能发现，宽度数据看不出来。

### ② 亮暗不联动：两处状态各自为政

用户原话："右上角的亮暗切换和主题中的亮暗切换并不实时联动。"

原因：标题栏那颗按钮只调 `applyTheme()`，它内部的 `commitTheme` 只刷新
**标题栏按钮自己的**图标；而主题页的 `.th-mode.is-on` 与卡头摘要是
`renderThemeSection()` 里算的，没有任何人通知它重渲染。

修法：监听 `qqa-theme-change`（`commitTheme` 每次都会派发），
**若渲染用的偏好已过期**才 `renderSettings()`。

⚠️ 不能无脑重渲染：`renderSettings()` 会重拉 config/skills 一堆接口，
而 `applyTheme` 在系统明暗切换、启动、甚至我们自己点亮度档时都会派发 ——
无脑重渲染会造成"点一下 → 重渲染 → 事件 → 再重渲染"的连锁与闪烁。
判断依据是卡头摘要文本与当前实际偏好是否一致，一致就不动。

### 顺手修掉三处测试脆弱点（都是批量跑才暴露的）

这一轮批量回归连红三次，每次都换一个套件 —— 但根因是同一类：
**用固定 `sleep` 代替真正的就绪等待**，于是读到未就绪的 DOM。

| 套件 | 现象 | 根因 |
|---|---|---|
| `check-theme` | `getComputedStyle(null)` TypeError | 导航后 `document.body` 还是 null，`sleep(2000)` 不够 |
| `check-personalize` | `Cannot read properties of null (reading 'click')` | 导航后 `#theme-btn` 还没被 `bind()` 挂上 |
| `check-log-fold` | `Cannot read properties of null (reading 'textContent')` | 等待条件只覆盖了运行日志，没覆盖**要读的应用日志** |

三条都改成明确的等待条件：
- `check-theme`：等 `document.body && data-theme`（内联脚本跑过）；
- `check-personalize`：额外等 `#theme-btn` 存在（DOMContentLoaded 之后才绑）；
- `check-log-fold`：等待条件列出**后续要读的每一个元素**。

> 第三条的教训值得单独记：**等待条件要按"后续读取的元素集合"来写**，
> 不是等其中一个就够了。只等 A 就去读 B，是这类假失败的固定套路。

### 还有一处：把"环境不具备"和"功能坏了"分开

`check-snowluma-live` 断言"25 秒内能收到 `snowluma-log` SSE 事件"。
它失败时收到 0 条 —— 但实测发现**机器人的 SnowLuma 日志文件在测试开始前 5 分钟就停写了**
（群消息稀疏时段）。两者现象完全一样，结论却相反。

`SnowLuma` 是用户独立启动的进程，它不输出时测试端**无从产生数据**。
所以判据改成先看日志文件最近有没有写：
- 25s 内有写入却没收到事件 → **真失败**（跟随器可能坏了）；
- 25s 内没有写入 → **跳过并说明原因**（"没数据可跟"，不是缺陷）。

这样它既不会在空闲时段误报，也不失去"有数据时必须推得出来"的把关能力。
（本轮实测：机器人恢复输出后这条立刻通过，收到 9 条事件。）

## 2026-10-06 第三十三轮：酒狐改成真实 BlockBench 模型

### 先说结论：手绘狐狸被否掉，换用用户提供的 .bbmodel

上一轮我自己画的像素狐狸（拆成头/身/尾等 SVG 部件、拼装定位）**看起来不像狐狸**。
把它放大 24 倍逐格看，问题一目了然：尾巴是个悬在空中的方块、头与身体糊成一个大矩形、
眼睛连成一片像面具。凭想象摆坐标做角色美术，就是在赌。
用户随后给了两份 BlockBench 模型，方向立刻清楚了。

**已全部删除**：`shell/04-fox-pet.js`（手绘版）、`styles/33-fox-pet.css`、
`tools/check-fox-pet.mjs`、`tools/shoot-fox-sprite.mjs` 与相关截图。

### 模型文件摸清的结构

两份都是**完整 Bedrock 模型**，不是"导出的图片"：

| | 大正女仆酒狐 | 魔法酒狐 |
|---|---|---|
| 立方体 | 490 | 1436 |
| 骨骼组 | 195（深度 18） | 291 |
| 贴图 | 2 × 256² | 6 × 256² |
| 动画 | 97 | 130 |
| 源文件 | 4.83MB | 4.03MB |

关键字段：
- `elements[]`：`from`/`to` 是模型空间轴对齐盒，`rotation`+`origin` 是**立方体自身**的旋转，
  `faces{}.uv` 是贴图矩形（**全是 box-uv，没有 per-face-uv**，这一点省了不少事）。
- `outliner[]`：既能是字符串（直接引用 element uuid），也能是对象（骨骼组，
  带 `origin`/`rotation`/`children`）。子节点可以是字符串也可以是对象 —— 递归时两种都要认。
- `animations[].animators`：**按骨骼 uuid 索引**，不是按名字。
  每个 keyframe 只有**一个** data_point，所以插值必须**跨 keyframe**做。
- 有 26422 个关键帧，绝大多数值是**数字字符串**（`"0"`、`"-32.5"`）。

### 为什么自己写软件光栅化器（而不是 three.js）

1. 本机**没有** three.js，离线环境也**不能下载**大包；
2. 模型是 Bedrock 格式（每面一个像素矩形 UV + 骨骼层级 + Molang 动画），
   用 three.js 也仍要自己写加载器与骨骼绑定 —— 省下的只是矩阵库那几行；
3. 自己写才能让**同一份数学在 Node 里预渲染、在浏览器里实时跑**。
   这一条价值最大：调坐标系/骨骼矩阵/UV 朝向时，能在 Node 出一张 PNG 直接看，
   不必开浏览器；而这类错误在浏览器里只表现为"模型没出来"，极难定位。

实现要点（都在 `app/ui/assets/fox/fox-model.mjs`）：
- 立方体**自身旋转在解析期就折进 8 个角坐标**（预计算），渲染时不需要再乘一次矩阵；
- 骨骼变换 = `T(origin) · R(anim) · T(-origin)`，从根往下累乘（顺序不能反）；
- 背面剔除 + 按平均深度从远到近排序 + z-buffer。**排序与 z-buffer 都要**：
  Minecraft 模型有大量共面方块，只靠 z-buffer 会闪烁；
- 像素级 alpha 测试（`< 8` 丢弃）而不是混合：MC 贴图是硬边像素风，
  混合会让边缘发灰，alpha 测试才是原本的观感。

### 体积：4.83MB → 422KB（关键帧重排 + 动画策展）

直接丢 .bbmodel 进去是不行的。实测（`tools/probe-fox-size.mjs`）字节分布：
**动画占 91%**（maid 2520KB / 2773KB）。

两刀砍下去：

**① 关键帧重排（省 47~65%）**。原格式每个关键帧一个对象：

```json
{ "channel": "rotation", "interpolation": "catmullrom", "time": 3, "x": "0", "y": "-32.5", "z": "0" }
```

26422 个关键帧里，`"channel":"rotation"` 与 `"interpolation":"catmullrom"`
这两个**完全相同的短串**被重复了两万多次。改成分组后元数据只写一次：

```json
"rotation": { "i": "catmullrom", "k": [[3, 0, -32.5, 0], ...] }
```

顺带把纯数字字符串转成真数字（解析后数值一致，但少两个引号）。

**② 动画策展（再省一大半）**。这两份模型的动画绝大多数是"手持道具"用的
（`hold_mainhand:sword`、`swing:spear`、`use_offhand:drink`…），
对一只趴在界面上的宠物毫无意义。保留 16 条通用动作
（idle/idle2/walk/run/sneak/jump/fly/attacked/death/swim/sit/sleep/climb/gui…）。

结果：

| | 源 | 重排后 | 重排+策展 | 最终（含贴图） |
|---|---|---|---|---|
| maid | 4.83MB | 965KB | **422KB** | 451KB |
| magic | 4.03MB | 1268KB | **884KB** | 1007KB |

贴图也从 base64 data URL 拆成**独立 PNG**（`extract-fox-models.mjs`）：
内嵌 base64 会膨胀 33%、无法被浏览器单独缓存、也让 `JSON.parse` 更慢。

### 踩到的坑：宿主服务器的 MIME 表缺 `.mjs`

第一次跑验证，模型死活不就绪。页面自己的 catch 把异常吞了（只 `console.error`），
所以**控制台什么都没打**。把加载链拆成五步在页面里逐步执行、把 error 的
`message` 返回出来，才拿到真话：

```
Failed to fetch dynamically imported module: http://127.0.0.1:3210/assets/fox/fox-model.mjs
```

而**同一个 URL 用 `fetch()` 是 200**。原因是宿主 `src/app.js` 的静态服务器
MIME 表里没有 `.mjs`，落到 `application/octet-stream`；
浏览器按 ES 模块规范**拒绝**把非 JavaScript MIME 的响应当模块加载。
只看网络面板完全看不出问题 —— 状态码 200、内容也对。

修法：给宿主补 MIME，并写成幂等脚本 `tools/patch-host-mime.mjs`
（顺带补齐 `.ttf/.otf/.woff/.woff2/.wav` —— 它们原本能工作只是因为
`@font-face` 与 `decodeAudioData` 比较宽容，但写对了才能正确缓存、便于排查）。
**重装 QQ Agent 后要重跑这个脚本**。

### 交互设计

- **按住拖动** → 移动位置（沿用上一版的 transform 方案，每帧改 top/left 会重排整页）；
- **横向拖动同时转身** → 系数 0.45 是手感值：1:1 太灵敏（拖 100px 转 100°，容易转晕）；
  纵向拖动改俯仰（限制 -30°~50°，避免转到"底下"看不见）；
- **单击** → 逗它（播一次 `attacked` + 说一句话）；
- **双击** → 转一圈；**右键** → 躲 6 秒（别挡着用户看内容）；
- 5px 阈值区分"点击"与"拖拽"—— 否则一次轻微点击会被当成拖拽，
  台词从"逗它"变成"放我下来"，很怪。

**性能三招**：① 按需重绘（静止且关了持续动画时完全不重绘）；
② 动画节流到 24fps；③ 画布内部分辨率固定 256²（不做 DPR 放大）——
像素风模型本来就不该抗锯齿，这同时把光栅化面积压到最小。
实测切模型耗时 2.6s（magic 1436 立方体 + 6 张贴图）。

## 2026-10-06 第三十四轮：用户纠正 —— 恢复原版动画，修默认姿态

用户反馈原话："你动画重绘干什么，原有的动画序列是好的，默认状态现在也没了，
现在的默认状态一团乱麻，给你一张酒狐的正面参考照，给我搞回来。"

### 我做错的两件事

**① 擅自"策展"了用户的动画数据。**
上一版我按自己的判断把 97/130 条动画砍到 16 条，理由是
"`hold_mainhand:sword` 这类手持道具动画对桌宠没用"。
**那是用户的素材，不是我的判断对象。** 现在已经**全量恢复**
（`extract-fox-models.mjs` 里的 `KEEP_ANIMATIONS` 白名单整个删掉）。

体积从 451KB/1007KB 回到 451→965KB / 1007→1268KB（合计 2.38MB）。
试过用二进制定点编码（Int16）再压 —— 实测**反而更大**：
省下的十进制文本被 Molang 字符串表和 base64 膨胀抵消了。所以不折腾，直接留 JSON。

**② 默认姿态是错的。** 我加载模型后放了 `idle` 动画，而不是**中性姿态**。
中性姿态 = 骨骼用 outliner 上的静态 rotation，也就是 BlockBench 里打开模型的样子。
现在 `DEFAULTS.anim = ''` 表示"静止在中性姿态"，动画只在用户触发时播。

顺带查清了一件事：我一度怀疑"某个动画才是默认姿态"，
于是写探针统计**每个动画在 t=0 时的非零通道数** ——
结果所有"看似中性"的动画（`pre_parallel*`、`hold_mainhand:empty`…）
**值全是零**，它们本身就是空动画。所以中性姿态确实就是静态姿态，没有更好的候选。

### ③ 取景用固定包围盒，不能每帧算

上一版每帧用**当前姿态**的包围盒定相机 → 动画一呼吸，包围盒变化 → 相机跟着缩放 →
画面里模型持续"一胀一缩"，看起来像在抖。这是"一团乱麻"的另一个来源。
现在在模型加载时用中性姿态算**一次**（`boundsOf` 导出到 fox-model.mjs），之后固定。

### ④ 蓝框的真相：模型自带的背景板

那个蓝框元素名全部是 **`Background1`**，尺寸 3×55×1，
而 55 正好等于整个模型的包围盒高度 —— 是作者**做在模型里的展示背景板**。
它把包围盒撑大，导致角色被缩得很小（只占画布宽度 45%）。

用户给的参考照里没有它，所以默认**不渲染**；设置里给了开关
（"显示模型自带的辅助几何"）想留着可以打开。
另外取景留白系数从 2.15 收到 1.8，角色现在占画布宽度约 62%，与参考照比例一致。

### ⑤ 默认视角改成正对镜头

原来 yaw=-22°/pitch=10°（斜着看），现在 yaw=0/pitch=0。用户给的参考照就是正面。

### ⑥ "待机动作"下拉：全部动画都能选

设置页新增下拉，选项 = **"（静止 · 模型默认姿态）" + 当前模型的全部动画**
（女仆 97 条 / 魔法 130 条，实测下拉 98 项）。
选项是**动态**从已加载的模型取的 —— 两份模型动画完全不同，写死一份必然对另一份失效。
这也兑现了"原有的动画序列是好的"：不是我挑几条给他，而是全都给。

### 本轮踩的坑：探针喂错格式，静默返回空

写"对比几种默认姿态"的探针时，我直接把**原始 .bbmodel** 喂给 `poseAt`，
但 `poseAt` 已经从"原始 keyframes 格式"改成读"紧凑分组格式"了。
结果**每个动画都返回 0 根骨骼变换** → `gui`/`idle`/不给姿态渲染出来一模一样，
对比图完全无意义。这类"格式不对但函数不报错、静默返回空"最难发现。
修法：探针里补一个 normalize 步骤，并在注释里写明为什么。

同一次还踩了个连带的：探针里贴图映射为空（原始文件的贴图在 `source` 字段，
而 `parseModel` 当时只认 slim 格式的 `file`），**渲染器拿不到贴图就静默 `continue` 跳过所有三角形**
→ 输出全白 + 0 像素，看起来像相机坏了。
已让 `parseModel` 同时支持 `source` 与 `file` 两种输入。

## 教训（写给以后的自己）

1. **不要替用户"策展"他的素材。** 体积问题用压缩解决，不用删数据解决。
   判断"哪些动画有用"不是我的职责 —— 我只看到文件名，他知道自己要什么。
2. **"默认状态"是有明确定义的**（中性姿态 / BlockBench 打开时的样子），
   不能拿一个看起来正常的动画去代替。
3. 探针脚本要**验证自己的输入**（变换数是不是 0、贴图是不是空），
   否则"静默返回空"会伪装成"功能坏了"，白查半天。

`check-fox-pet.mjs` 相应更新：断言**全量保留**（>90 条）而不是"我留下的那几条在"，
断言默认是 `(neutral)` 且 `showDecor=false`，断言待机动作下拉含"静止"且 >90 项。
一键回归仍为 **39 个套件**，588 秒全绿。

### 本轮踩的坑：`!= null` 吃掉了 `false`

设置页"辅助几何"开关点了没反应。原因是我这么写：

```js
if (patch.showDecor != null) drawFrame(true);
```

而 `showDecor` 的默认值是 **`false`** —— `false != null` 求值为 **`false`**，
所以"关掉它"这个操作永远不触发重绘。判断"patch 里有没有这个键"必须用 `in`：

```js
const affectsRender = ['yaw','pitch','anim','showDecor','size'].some((k) => k in patch);
```

**布尔默认值是 false 时，这类"假值把存在性判断吃掉"的坑必踩。**

连带还有一个：`decorWanted` 这个模块级变量只在 `drawFrame` 里被赋值过，
首次挂载时根本没读偏好 —— 于是开关即使触发了重绘也读的是旧值。
现在在 `build()` 里显式读一次。

不要一头扎进代码里找错。

## 2026-10-06 第三十六轮：修正正面朝向（两个模型朝向并不相同）

用户反馈："让酒狐的正面对准屏幕，现在是反过来的。"

### 结论：**maid 本来就是正的，magic 才是反的**

第一反应是"把 yaw 加 180 就行"，但那样会把本来正确的 maid 转反。
所以先出图验证，而不是直接改数：

| 模型 | yaw=0 | yaw=180 |
|---|---|---|
| maid（大正女仆酒狐） | **正面**（脸 + 和服朝镜头） | 背面 |
| magic（魔法酒狐） | 背面 | **正面**（裙子正面 + 法杖朝镜头） |

`magic` 特别容易误判：它的**魔法阵几何建在角色前方**（Z ≈ -29 ~ -34），
yaw=0 时那圈阵正好糊在身体前面，看起来"又是一团紫色的东西"，
很容易被当成"模型坏了"或"朝向反了"。
`maid` 的朝向我还额外用**页面画布导出**验证了一次（不是只在 Node 里渲染）。

### 做法：把"正面朝向"变成模型自身的属性

不是全局写一个 yaw，而是加 `facing` 字段：

- `tools/extract-fox-models.mjs` 的 `FACING = { maid: 0, magic: 180 }`
  → 写进 `manifest.json` 与 `<id>.model.json`；
- 运行时有效视角 = `model.facing + 用户偏移`（用户偏移默认 0）。这样：
  - 默认就是正面；
  - 以后加新模型只需填 `FACING`，不用改渲染代码。

⚠️ `facing` 必须**同时写进 manifest**。运行时是先读 manifest 拿到模型列表
与朝向，再 fetch 各自的 model.json —— 只写进 model.json 的话，
列表阶段拿不到 facing（这一版我就漏了 manifest，表现为 magic 仍旧背对镜头）。

新增可复用工具 `tools/shoot-fox-facing.mjs`：在**页面里**依次切两个模型、
各导出一帧画布并拼成一张对照图。以后加模型/改朝向用它一次就能确认。

### 本轮踩的两个坑

1. **"反了"的三种可能要分清**：yaw 反（左右翻转）、pitch 反（上下翻转）、
   模型本身建反。我把 pitch 从 -22 扫到 30 逐一出图，确认
   **pitch 不会导致左右翻转**，从而排除掉一个错误假设 ——
   否则就会去改 pitch，越改越乱。
2. **拼图时用了第一块的宽度**：maid 画布 256²、magic 224²（见 `canvasResFor`），
   我却统一按 256² 去读 magic 的数据 → 越界取到 0 → 导出成一片白，
   看起来像"magic 渲染坏了"。**不同尺寸的图拼在一起时，每块必须用自己的 w/h 索引。**

### 关于"应用被系统杀掉"

调试期间 QQ Agent 多次整个进程消失（`AppHangTransient`，且日志无任何异常堆栈）。
定位下来主因是**机器内存紧张**：全量回归跑到后半段只剩 2.5~4 GB 可用
（15.7 GB 总量，Edge/QQ/企业微信等已占大半），进程被系统回收。

为此给宠物加了三条**保守措施**（不影响观感，但显著降低主线程占用）：

1. `canvasResFor()`：画布内部分辨率按模型规模自适应
   （maid 256²、magic 224²），不再固定 384²。软件光栅化是同步跑在主线程的，
   开销 ≈ 像素数 × 面数；384² 比 256² 贵 2.25 倍。
2. `frameInterval()`：动画帧率**按实测渲染耗时自适应**
   （间隔 = max(1/20s, 上帧耗时 × 1.5)），保证至少 1/3 的时间留给界面本身 ——
   宁可动画掉帧，也不能让应用失去响应。
3. `document.hidden` 时**直接停掉 rAF 循环**（并用 `visibilitychange` 接回来）。
   回归测试会开多个标签页并留在那儿，不可见页面还在跑同步光栅化纯属浪费。

另外把"待机动作下拉"的填充改成**带重试**（最多 3 次、间隔 800ms）：
模型加载 = 动态 import + fetch 近 1MB JSON + 解码贴图，机器忙时可能几秒才回来，
而"下拉是空的"对功能来说就等于坏了。测试侧也改成等**内容就位**再断言，
不再用固定 `sleep`——这是本项目反复出现的一类假失败。

## 2026-10-06 第三十七轮：朝向 —— 以用户参考照为准，并加「一键翻转」

`maid facing=0`、`magic facing=180`，渲染结果与参考照一致。

### 但为了让这件事**一次终结**，加了逃生口

不再依赖我和用户之间来回判断，而是把决定权交给用户：
设置页加了一个「**翻转 180°**」按钮，点一下即翻，并显示当前是"正面/背面"。

- `DEFAULTS.flip = false`；有效 yaw = `model.facing + 用户偏移 + (flip ? 180 : 0)`；
- 翻转是**持久化**的（写进 `qqa-fox`），不是临时状态；
- 这样即使我和他对"哪面是正面"的理解仍然不同，他点一下就能得到他想要的，
  不需要我再改代码、也不需要再等一轮部署。

### 新增可复用工具

- `tools/shoot-fox-facing.mjs` —— 在页面里依次切两个模型、各导出一帧画布并拼图，
  用于确认朝向；
- `tools/shoot-fox-window.mjs` —— 截**整窗**（含 CSS 缩放）。之前只对比"导出画布的像素"，
  绕过了 CSS，看不到窗口里的真实观感；有了整窗截图才能和用户的截图直接对齐。

### 测试补强

`check-fox-pet.mjs` 新增四条断言：
1. 每个模型都在 `manifest` 里声明了 `facing`（**朝向来自数据，不硬编码在渲染里**）；
2. 默认 `flip` 关闭；
3. 「翻转 180°」确实会改变画面（像素统计有变化）；
4. 朝向切换不会把画布画空（翻转后仍有合理的不透明像素）。

第 1 条是针对本轮教训加的：我在这一个点上反复改错过，
把"朝向"变成**可断言的数据**能防止它再被手滑改反。

### 一句总结

**当我和用户的观察不一致时，先怀疑自己手上的证据是不是过期了**，
而不是立刻按对方的话改 —— 但也必须给对方一个"立刻能自己纠正"的开关，
否则就会在一个只有他能看到结论的问题上无限往返。

## 2026-10-06 第三十八轮：回答"脸为什么糊"与"刷新后又反了"

用户两个问题（附两张图：①窗口里糊糊的酒狐 ②Minecraft 里正常的酒狐）。

### ① 脸为什么糊 —— 三个原因叠在一起

| 原因 | 说明 |
|---|---|
| **分辨率低于显示尺寸** | 画布固定 256²，而默认显示宽是 300px（当初为"大一点"从 210 提上来的）。把 256 的图**放大到 300** = 1.17 倍插值。 |
| **`image-rendering` 写反了优先级** | CSS 里先写 `pixelated` 后写 `crisp-edges` —— **后写的生效**，于是用了 `crisp-edges`。它在 Chromium 上走的是一种"边缘保持"的平滑算法，对**透明底**的像素画会把 alpha 边缘重采样成半透明像素，1~2 像素的眼睛/嘴直接糊掉。 |
| **画布是正方形** | 模型真实比例是 44.8 宽 × 55 高 ≈ 0.81（竖长），却塞进方框里，上下留白多、角色偏小。 |

修法：
1. `canvasResFor()` 改成**按显示尺寸给分辨率**（×1.1 余量，上限 448²，
   魔法酒狐那档封 352²）——现在渲染 352×429 / CSS 320×365，**缩放比 0.91×**，
   也就是**缩小**而非放大，细节不再丢；
2. CSS 把 `pixelated` 放到**最后**（后写生效），并注明原因；
3. 新增 `canvasAspect()`，画布按模型真实比例给高宽（女仆 0.82、魔法 1.0），
   角色填满可视区。

额外把动画帧率上限从 20fps 降到 16fps、分辨率上限从 512² 收到 448²：
512² 那一档实测会让 QQ Agent 被系统回收（见下面"内存"一节）。

### ② 刷新后又反了 —— 是"手动翻转"与"默认朝向"叠加了

我之前给的「翻转 180°」是**叠加**在 manifest 的 `facing` 之上的：
用户点过一次 → `flip=true` 存进 localStorage → 刷新后仍然生效。
而我中途又把 manifest 的默认 `facing` 调过头，
于是"新默认 + 旧 flip"两者叠加，画面**又**翻回去了 ——
也就是"改了默认值，用户那边反而更乱"。

两个修法：
1. **把默认朝向调成他实际看到的正确那一侧**：`maid facing=0`、`magic facing=180`
   （依据：他给的"正常酒狐"参考图能看见脸，而只有 `maid yaw=0` 能产出正脸），
   目标是**刷新后开箱即正，不需要去设置里手动翻转**；
2. 新增 `facingVersion`：**每次调整 FACING 就 +1**，读到版本不一致时自动把
   `flip` 复位为 false。这样以后我再改默认值，也不会和用户存下的 flip 打架。

### 关于"两侧看到的画面左右相反"

我这边的渲染与用户的窗口截图长期是 180° 相反的，这在几何上很可疑
（同一份模型 + 同一套相机数学不该出现），更像**窗口/截图链路层面**的差异。
但因为无法直接看到他的屏幕，我采取的策略是：
**默认值以"能出正脸"为准**（他给的参考图就是判据），
同时保留一键翻转作为他自己的微调入口 —— 不再靠我猜。

### 内存与崩溃

这一轮里 QQ Agent 又整个进程消失过一次（同样是 `AppHangTransient`、
日志无异常堆栈）。原因是把分辨率上限提到 512² 后单帧成本翻倍，
而这台机器 15.7GB 内存、跑回归时可用只剩 2.5~4GB。

`buildTriangles` 的骨骼递归是本项目最多灾多难的一段。三次错误形态不同：

| # | 写法 | 症状 |
|---|---|---|
| ① | 先 `T(origin)` 再 `R`（把 pivot 当绝对平移） | 195 根骨骼各平移一次，模型撑到 **454 单位高**，角色散架 |
| ② | `T(p)·R·T(−p)`，且把结果整个传给子级 | 外框看似正常，但 `T(−p)` 把**整棵子树拉回原点**：尾巴世界 pivot 全是 (0,13,24.9)，**尾巴从身体前面垂下来** |

```

```

所以绝不能再把父级的累积位移加一遍。

## 2026-10-06 第四十四轮：六项界面修复（MC 亮色 / 拉杆统一 / 点击音 / 输入框对齐 / 撤销按钮 / 顶栏配色）

用户一次报了六条，逐条落地。**每条都配了可量化的验证**，不靠肉眼判断。

### ① MC 亮色模式"灰蒙蒙"

原因：亮色底用的是 MC 经典 GUI 的深石板灰 —— `--q-bg-base: #d8d8d8`、
卡片面 `#c6c6c6`。大面积中灰 + 更暗的卡片，观感确实又闷又脏。

改法：**整体提亮一档并让卡片浮起来**（卡片面比底更亮）：
`base #d8d8d8 → #ebebeb`、`bg1 #c6c6c6 → #f6f6f6`、`bg2/bg3/line*` 同步调整，
`--q-bg-sidebar` 跟着 `#f6f6f6`。正文色一并加深（`--q-fg #2b2b2b → #1f1f1f`）保住对比度。

### ② 所有开关统一成"小拉杆"（含动效）

用户原话："所有开关都应该用二级设置中的小拉杆形式（包括动效），
如图一所示的开关仍然为原版，极度违和。"

根因很好玩：MC 的拉杆**画在 `input[type=checkbox]` 自身上**
（`::before` 石座 + `::after` 木杆）；而设置页那批开关用的是 `.switch` 组件，
它把复选框**视觉隐藏**了（`opacity:0; width:0`），显示的是 `.track` + `.thumb` ——
所以拉杆根本画不出来，落回"胶囊 + 圆点"。

改法：把 `.track` 当石座、`.thumb` 当木杆，在 MC 皮肤下重做外观
（30×18 灰石凹槽 + 8×16 木色握把 + 开态红石光）。
⚠️ **只平移不旋转**：真拉杆那样绕底端转 38° 会把握把甩出轨道、在卡头那种
紧凑行里盖住文字。选择器必须带 `html[data-skin=…]` 前缀，否则压不过
40-market.css 里特指度更高的 `.switch .track`。

实测：14 个开关全部变成 30×18 / 8×16 的拉杆。

### ③ 开合页面卡也要有声音

`CLICKABLE` 白名单里没有 `.setcard-head`，所以点卡头（整行可点、`cursor:pointer`）
**一声不响**，手感很空。补了一条针对卡头的委托。
⚠️ 没有把 `.setcard-head` 塞进白名单：卡头里的按钮本来就会被白名单命中，
再算上卡头就会**响两声**。所以判据是"点击目标不在卡头内任何控件上时，才补卡头音"。

### ④ 输入框不对齐

`.field-row` 是 `display:flex; flex-wrap:wrap`，而 `.field` 的基准尺寸取
**min-content** —— 由最长的标签词决定（例如"禁言时长（分钟，0 = 直到手动解除）"）。
于是同一行里输入框一块宽一块窄，上下两行的起点也错开。

改法：`.field-row:has(> .field)` 改用 grid 等分
（`grid-auto-flow: column` + `grid-auto-columns: 1fr`），
对 2 列和 3 列的行都成立，不用为每行写死列数；`.field` 加 `min-width: 0` 允许收缩。
窄屏（≤760px）退回单列。

实测：指令禁言 2 列 **460/460**、主动开话题 3 列 **303/303/303**，顶边与高度全一致。

### ⑤ 「撤销本次设置」不改变高度 + 位置贴标题

原来 `form.prepend()` 成独立块级行 → 一出现就把内容往下顶（高度跳动），
而且悬在表单最上方、离它要撤销的那块标题很远。

改法：插到区块 `<h3>` 内部，h3 变成 flex 标题行（标题文字包一层 span）。
按钮高度压到 20px < h3 行高 22px，所以**高度零增量**。

实测：出现前后表单高度 **1904 → 1904**、标题行 **22 → 22**，按钮在 h3 内、同一行。

⚠️ 顺手修掉一个**隐性 bug**：`showUndoBtn` 只判 `if (undoBtn) return`，
而 `renderSettings()` 会整体重建表单 innerHTML、把按钮丢掉，但 `undoBtn`
变量仍指向**已脱离文档**的旧元素 → 此后再也不会重建按钮。
用户看到的现象是"撤销按钮出现过一次、之后再也不出现"。
判据改成 `isConnected`（按钮还在不在文档里）。已加断言锁住。

### ⑥ 顶栏底色与导航栏一致

先**量**再改（`probe-surface-colors.mjs`）：MC 亮色下顶栏是不透明的
`rgb(216,216,216)`，而侧栏/内容区/功能条都是 62% 半透明的 `--q-bg-1` ——
顶栏确实比它们都沉。

改法：新增独立令牌 `--q-bg-titlebar`（缺省回落 `--q-bg-base`），
在 32-theme.css 里 MC 皮肤把它指向 `--q-bg-sidebar`。用一个令牌把这件事
"可调"，而不是每次改都去动 02-titlebar.css 那条背景声明 ——
因为这里曾被两版需求来回拉过（2026-10-04 的"无痕"要求顶栏与内容同色，
理由是暗色下两者差 6 级明度会出现一条横贯整窗的色差线）。

实测：MC 亮色下 顶栏 **rgb(246,246,246)** == 侧栏，内容区 **rgb(235,235,235)** —— 区分开了。

### 附带：一个既有缺陷（与主题无关）

排查过程中撞上"设置页渲染失败：Cannot read properties of null (reading 'api'/'tools')"。
根因：`state.config` 只在那 7 个请求的 `Promise.all` **全部完成**后才赋值，
而 `renderApiSection` / `renderToolsSection` 是**直接解引用** `c.api` / `c.tools` 的
（全设置页只有这两处没有 `?.`）。配置没到就渲染 → 抛错 → 整块变成一行红字。

改法：`renderSettings` 里先判配置是否存在；缺就渲染一个**加载态**并自动重试
（最多 10 次 × 700ms，成功后恢复正常渲染）。最坏是"多转一会儿"，不再是"一片报错"。
`renderToolsSection` 另加 `(c || {})` 兜底。

### 排查教训（值得单独记）

我一度以为"配置永远加载不到"，查了很久 —— 实际是**我的探针写错了**：
`page.eval('switchTab("settings")')` 里的 `switchTab` 是**模块作用域**函数、
不是 window 属性，在页面全局求值直接 ReferenceError；
而我用 `try{}catch{}` 把它吞了，于是"点了设置页但什么都没发生" ——
`loadSettings()` 没跑 → 配置始终 null → 设置页渲染失败。
**这在界面上看起来完全像应用坏了，实际是探针没点对。**
教训：**模拟用户操作就点真实元素**（`document.querySelector('.tab[data-tab="settings"]').click()`），
别去调内部函数；`try/catch` 吞异常会让"没执行"伪装成"没效果"。
