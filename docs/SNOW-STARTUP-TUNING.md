# SnowLuma核心与插件加载调查

2026-10-07。本轮用户询问核心能否修改并指出仍慢；仅本地修改和验证，没有上传GitHub。

## 可修改范围

安装版SnowLuma为1.14.19，内置Node 22.13.0。index.mjs约7.45MB、23万行，是可读的构建产物，WebUI、配置、日志分别在分块JS中；当前目录没有原始TypeScript工程或source map。可以为运行版打可回滚补丁，但不把打包代码称作完整源码。

底层注入、协议相关实现含native/*.dll与*.node；本次未找到对应原生源码，不修改二进制，也不改账号、自动注入规则或消息协议。

QQ Agent Electron 33.4.11内置Node 20.18.3，不支持Node 22的原生module compile cache，因此不能将SnowLuma的缓存方法直接套在宿主插件加载器上。

## 本地调整

`tools/patch-host-snow-startup.mjs`验证所有锚点再修改src/app.js与snowluma/index.mjs，保留原字节备份，写入失败回滚，重复运行幂等。

- SnowLuma启动子进程设置独立NODE_COMPILE_CACHE，放在snowluma/data/.arcfox-compile-cache；仅影响子进程，不写全局环境变量。
- 核心初始化后flushCompileCache，将已编译模块写入缓存，避免Windows强制结束进程时跳过退出钩子而丢失缓存。缓存失败不阻挡业务。首次运行建立缓存，后续进程启动才可能受益，源码改变由Node重新编译。
- 宿主检测SnowLuma就绪间隔从1000ms降为200ms，仍直接探测实际WebUI端口、20秒墙钟截止，保留取消检查。只是更快识别就绪，不改变注入和登录完成的判断。额外回环探测只存在于启动窗口，非永久高频轮询。

## 两次测量

基于上轮异步窗口补丁，完整退出后启动；从main.js探针计时，不包含进程装载，不是清空文件缓存的磁盘基准。

| 指标 | 第一次建立编译缓存 | 第二次使用缓存 |
|---|---:|---:|
| 窗口显示（累计） | 1.857秒 | 1.841秒 |
| SnowLuma准备耗时 | 0.923秒 | 0.708秒 |
| 37个插件加载耗时 | 1.275秒 | 1.279秒 |
| 插件模块导入累计 | 0.911秒 | 0.931秒 |
| 插件setup/register累计 | 0.049秒 | 0.053秒 |
| 核心准备完成（累计） | 2.813秒 | 2.815秒 |

缓存确实落盘（5个文件，约1.49MB）。这两次数据显示SnowLuma检测准备约0.7–0.9秒，但整体准备已由插件主导，没有证明总体启动进一步缩短；文件缓存、系统负载和200ms轮询都会影响差异，不能把0.215秒全部认定为编译缓存收益。

插件导入是主要耗时阶段，注册本身只有约50ms，盲目并行register/setup不能解决主要瓶颈。现有加载器特意按目录顺序执行，涉及同名工具覆盖、能力注册、旧实例deactivate/dispose与失败恢复；本轮没有改变该顺序，也没有声称插件已经提速。

下一步若继续优化插件，需拆分模块准备与顺序注册，并审查模块顶层副作用和依赖；或重建支持Node 22+的Electron宿主后评估编译缓存。当前不为节约1秒直接替换整个运行时或改变未知插件执行语义。
